# 怎么先找到「还没被守住」的地方：换尺子，不是再读一遍代码

从 `CONTRIBUTING.md` 拆出来的**参考篇**。规矩清单讲的是「一条守卫会怎么失效」，
这里讲的是动手之前的下一步：用哪几把尺子去量「哪里还没被守住」。用的人少得多，
所以不占着那份清单的位置 —— 但两边的结论是同一套：**读代码读不出缺口，得换尺子。**

规矩清单里讲**守卫怎么失效**那一节（写守卫必须做变异验证）说怎么坏，这里讲动手之前的下一步：**怎么先发现哪里还没被守住**。

2026-08-20/21 连着用了**十种**查法，产出差得很远，而差别与「代码看起来对不对」几乎无关，
只与「**这把尺子以前有没有量过**」有关：

| 查法 | 产出 | 适合找什么 |
|---|---|---|
| 读判据、找说明里的自承缺口 | 0 —— 全是叙述历史或已定论的取舍 | 已经被想过的问题 |
| 对着真实职位库跑 `tools/audit_pipeline.py` | 0 新的 | 数据层面的规则漏洞 |
| **量 `tools/` 的行覆盖率** | **9 处** | **判据停在「东西在不在」的那一类** |
| **读产品真正交付的产出** | **5 处** | **模板里的字被逐字抄给用户、报告自己少报** |
| AST 扫「恒真的断言」 | 0（尺子验过会亮） | 断言写了却不可能失败 |
| 扫文档里写的工具调用与开关 | 0 —— **而且发现早就有判据在管**（`ToolFlagsResolve`） | 教用户敲一个工具不认的参数 |
| 扫「定义了没人调用」的函数 | 0 —— **故意不固化**（启发式，会误报） | 规则声明了、另一头没落点 |
| 产物的生产者/消费者图 | 0 | 同上，从数据这一侧看 |
| **像执行者一样通读一份工作流** | **2 处** | **步骤顺序、伪代码与表自相矛盾** |
| **把 markdown 渲染出来看** | **3 处** | **块结构：源码逐行都对，渲染出来是另一回事** |

**产出最高的两把是「量执行」和「读产出」——都不是读代码。**
行覆盖率那九处没有一处是「忘了写测试」，全是测试写了、但没走到要测的东西：
把函数打桩换掉、只 `hasattr` 加源码文本比对、只验链条的形状不验它通不通、
夹具里恰好没有触发那一支的数据。**这层差别读代码看不出来，只有量执行才看得见。**

没装 `coverage` 也能量：Python 3.12+ 的 `sys.monitoring` 可以只给 `tools/` 里的
code object 装 `LINE` 钩子（`set_local_events`），别处零开销，整套测试跑完只慢一点。

> **这个探针本仓库不附带**（约 60 行，一次性用完就丢，不值得当成要维护的工具）。
> 要重建它：import `tools/*.py` → 递归收集它们的 code object → 逐个
> `set_local_events(tool_id, code, LINE)` → 原地 `unittest.discover` 跑一遍 →
> 拿 `code.co_lines()` 的行号集合减去命中集合。回调里 `return sys.monitoring.DISABLE`，
> 命中一次就够。

## 读产出：最容易被跳过、产出却最高的一把

前面几把量的都是「我们写的东西对不对」。**读产出量的是「它产出的东西长什么样」**——
把工具真的生成的文件拿出来数一遍。2026-08-21 扫六类产出（投递话术 236 份、
评估 268 份、JD 快照 284 份、投递台账 83 行、简历审计、学习计划），出了 5 处修补，
形状高度一致：

- **模板里出现的字会被逐字抄给用户**（话术抬头写着「判词」、简历审计的小节名写着
  「能力边界」——都是 `AGENTS.md` 明令不上台面的框架词）；
- **报告自己在少报**（审计的漏判统计写死 `most_common(3)`，七道门只报三道）；
- **数出来是 0 的那一格最值钱**（某个归档文件 285 个目录里 0 份，
  顺着查出它在仓库里有**两个名字**，写它的和读它的永远碰不上头）。

**「产出为空」不报错、不缺页，只是那一格是 0——要去数它，才看得见。**

## 用仪器之前先证明它会亮

覆盖率工具最危险的失效方式是**少报**——把「测过的」说成「没测过」，
于是你去补一堆本来就有的测试，还以为找到了缺口。所以先自检：
钩住一个函数、真调一次、确认记到了行。扫描类的工具同理——先喂一份**已知有问题**的
输入，确认它报出来，再信它的 0。

读数还要会打折：`def` 那一行在装钩子之前就执行过（假象）；`main()` 的 argparse
由 `--help` 的子进程测试覆盖（假象）；`lint_skills` / `security_guards` /
`verify_pdf` / `doctor` 的测试整体走子进程，进程内量不到（假象）。
**滤掉这三类之后剩下的才是真空白。**

## 变异测试自己翻车的三种方式

上一节说变异要「有效」。实测还有三种更蠢但更常见的翻法，都会让你把没验过的当成验过：

- **`errors` 不是 `failures`。** 类名/路径写错时 unittest 报
  `FAILED (errors=1)`——那是「找不到这个测试」，不是判据抓到了东西。
  **只有 failure 才算变异被抓住。**
- **变异把模块改成语法错误。** 往 f-string 的表达式里塞 `# 注释` 就会；
  模块根本没导入成功，而如果你只 grep `^(Ran |OK|FAILED)`，
  **什么都匹配不到，看起来像「跑了但没红」**。
  变异之后先确认「模块还能导入、测试真的跑了」，再看它红不红。
- **连着改同一个 `.py` 时，`.pyc` 会给你一个假红。** 前两种是「没红当成红」，
  这一种反过来：**跑的根本不是你刚写进去的代码**。CPython 判断字节码缓存新不新
  用的是源文件的 mtime，而它的粒度撑不住「一秒内连改两次」——批量跑变异正好是
  这个节奏，于是第二个变异跑的是第一个变异编译出来的 `.pyc`。
  实测（2026-08-23）：同一个常量在 60/70/80 三个取值上各跑三轮，
  **80 那一档绿一次红两次**，而它本该稳定绿；加上 `PYTHONDONTWRITEBYTECODE=1`
  之后九次全部一致。
  **凡是变异改到可执行代码（不只是注释和 docstring）的批量脚本，
  一律带 `PYTHONDONTWRITEBYTECODE=1` 跑。** 改文档字符串不受影响 ——
  那类断言读的是源码文本，不是字节码。

  **它还会活过脚本本身。** 2026-08-26 实测：把 `max(known)` 换成 `min(known)`
  验一条守卫，脚本跑完、源码还原、`git status` 干净、那两行 `grep` 出来也对 ——
  而**之后每一次单独跑那个测试仍然是红的**，跑的是残留的 `.pyc`。
  差点据此去「修」一个并不存在的 bug。
  这一次特别难认，因为 `min`/`max` **长度相同**：CPython 判缓存新不新看的是
  源文件的 mtime（秒）**加大小**，长度一变就必然重编译，而单字符对调两样都没变。
  单字符对调（`>=`↔`>`、`and`↔`or`、`min`↔`max`）正是最常用的变异形状。

  **认它的办法是别信 `git status`** —— 源码干净不代表跑的是源码。
  测试红得莫名其妙时，先 `find . -name __pycache__ -type d -exec rm -rf {} +`
  再判断。

## 恢复变异**绝不能用 git**

`git checkout -- <file>` 不是「撤销我刚才那个变异」，是「把这个文件退回 HEAD」。
工作树里有未提交的改动时，**它会连着那些改动一起抹掉**。

2026-08-21 实测代价：为了验一条判据，把某份工作流变异之后用
`git checkout -- workflows/job-setup.md` 恢复——**229 行未提交的翻译当场消失**。
（找回来了：干净 clone 实测留下的那份拷贝正好是翻译之后建的。**那是运气，不是流程。**）

正确的做法只有两种：

- **先把原文存起来**（变量里、临时文件里），恢复时写回去；
- 或者用**精确字符串替换回去**——变异改了什么就换回什么，别动别的。

改完一定要**另跑一条命令独立复查**文件已还原（`grep -c` 那个标记 + 语法检查），
不要信自己「我恢复过了」——本仓库有过变异脚本挂在超时里、恢复那一步根本没执行的实测。

## 造新尺子之前先搜一遍

**本轮实测代价**：为「文档里写的 `--flag` 工具认不认」造了一条新判据，
写完、变异验过、记录写完，才发现 `test_cross_references_resolve.ToolFlagsResolve`
**早就在做同一件事**，而且做得更好——它用子进程跑真 `--help`，
所以像 `--user` 这种由 `_cli.resolve_user` 统一加、源码里搜不到的开关**天然就被认出来**，
不需要我那个 AST 特例。新判据当场删掉。

漏搜的原因很具体：我只查了名字最像的 `test_index_matches_the_workflows`
（它管的是**斜杠命令**的开关），就断定「shell 里敲的那行没人管」。
**判据的文件名不按它守的东西命名**，`grep` 关键词才是可靠的入口——
搜 `python tools/`、搜那个概念本身，别搜你以为它该叫什么。

**再撞一次同一个坑之后，多认出一条机械的入口：豁免条件就是残留名单。**
`PythonNamesResolve` 里那行 `if "却把函数名写成了" in ln or "查无此" in ln`——
它不是随手写的通融，它是**判据自己撞上自己反例时留下的疤**，每一处都指向正文里
一段「复述坏例子」的叙述。顺着它去读，命中就是该清理的正文；
而这类叙述本身没有留存价值（它记的是修改史，不是事实），清掉之后豁免条件
可以原样留着继续防下一次。**判据里凡是「跳过某种行」的分支，都值得当名单读一遍。**

2026-10-14 那次量出来的实际数字：先按「反引号里是 `模块.符号`」粗扫，30 份文档命中 69 条，
其中 **68 条是文件名误报**（`` `serve.py` `` 被拆成 `serve` + `py`）——
与 2026-08-21 那次「30 条里 29 条」同一个坑，**仪器先挨怀疑**这条也复现了一次。
收紧到真符号之后，全仓 `workflows/` + 根文档 + `tools/` 注释里的死引用**归零**。

**搜到了要打开看，别只读命中行。** 2026-08-21 第四次撞车就栽在这儿：
搜 `n_processed` 时 `test_pipeline_counts.py:110` 就在结果里，那一行写着
「第一版调的是 `doctor._n_processed(seen)`」——看着像历史注释，就没打开文件。
打开才会看到下一句：**「验了零件，没验那条路」**，而那条既有判据跑的正是整条路，
比我要新建的那条强。**命中行是索引，不是结论。**

**自查重复本身就是一种找 bug 的手段。** 要判断「是不是重复」，
就必须去读那条既有判据**到底守什么**——而它守得往往比它自己以为的窄。
2026-08-21 实测：查重时读 `test_one_file_one_tolerance` 那张手工表，
发现它漏了 `doctor`；顺着把判据从只抓裸 `["seen"]` 加宽到也抓 `.get("seen", {})`，
**当场又抓到 `build_dashboard` 与 `gap_split` 两处同类 bug**。
查重那一趟的产出，比原本要新建的那条判据大得多。

还有一种「看着重复其实不是」：**两条测的是同一件事的两个实现**。
`test_dashboard_matching` 测 `build_model`（只有测试在调的夹具），
`test_materials_and_status_reach_the_panel` 测 `export_web_data.main()`（真跑的那条）。
**两条都要留，而且要互相点名**——否则下一个人会当重复删掉其中一条，
而被删的很可能正是测生产路径的那条。

**同一天犯了两次**：又为「读 JD 的命令要复述信任边界」新建了一条，
而 `EveryJdReaderRestatesTheTrustBoundary` 早就在做——类名就是那句话。
第二次的收获比第一次大：那条判据的名单是**手工维护**的（注释写着「记得往这里加」），
而它正是靠这一点漏掉了两条命令。**手工名单 + 一句「记得加」= 迟早会漏**，
所以并入时给它补了一条推导校验，而不是只补两个名字。

## 最后一把：像执行者一样通读

前面几把都是机械扫描，而**扫描预设了「问题长什么样」**。有一类问题没有形状可扫：
**步骤顺序**。

2026-08-21 通读 `/job-auto` 的循环时读出来的：`--target` 的跳出判据排在「补货」之后，
而 `/job-rank` 会评到排空、补货那一支以「回到 1」收尾——**那一步永远够不着**，
`--target 20` 攒够了照样继续抓。同一份文件的停手条件表里却明写着
「达到 `--target` → 正常结束」。八把机械尺子一把都没扫出来。

**读的时候把自己当成照着做的那个执行者**，一步一步走：这一步之后我在哪？
下一步够得着吗？这个分支有出口吗？——比「这句话对不对」有用得多。

## 第十把：把 markdown 渲染出来看

前九把量的都是**源码**。而 markdown 有一层源码里看不见的东西：**块结构**。

2026-08-21 实测三处，形状各不相同，共同点是**逐行读全都对**：

| 文件 | 源码里 | 渲染出来 |
|---|---|---|
| `job-auto.md` | 「停手条件」9 行的表，中间插了段 `> ⚠️ …` | 表只剩 2 行；**另外 7 条**（含「用户喊停」「达到 `--target`」）被块引用吸成一段带竖线的灰字 |
| `cdp-portals.md` | 额度表的后 3 行 | 被两个后插的 `###` 小节冲散，成了没有表头的孤儿行 |
| `job-scrape.md` | 猎聘那格写 `` `
` `` `` `
` `` `` `	` `` | **代码格里装的是真控制字符**，一行劈成三行：表格多出 2 条空行、加粗没闭合、正文断在半句 |

第三处最值得记：它在 `HEAD` 里就是坏的，而且成因就是本仓库反复栽的
**unquoted heredoc 吃掉一层反斜杠**——`
` 落盘时成了真换行。
写 markdown 里的转义序列时用 `chr(92)` 拼，或者用 Write 工具。

**两把尺子要一起用，它们互相漏。** 真渲染（`markdown` 库）漏掉了第三处
——python-markdown 把那两行吸成了空表格行，没留下裸竖线给探针抓；
而按 GFM 块规则自己走一遍的那份复刻抓到了它。反过来，复刻不管块引用里的表。
判据落在 `tests/test_tables_survive_rendering.py`（**不 import `markdown`**：
本仓库对外声明只用标准库）。

> **借别人的枚举器之前先看它量的是哪一段。** 这条判据第一版复用了
> `test_docs_track_the_framework._all_docs`，而那个函数的 SKIP 里带着
> `workflows`——于是判据只扫了 18 份，**三处发现所在的目录一份都没扫到**，
> 全绿。是变异验证（把真文件改回坏的，看判据亮不亮）才把仪器自己的毛病翻出来。
>
> 现在那条判据带一个**份数下限**（`FLOOR = 60`）。全绿有两种可能——
> 真没问题，或者根本没扫到东西；下限把后者变成红。**任何全仓扫描都该带一条。**

## 什么时候该停

不是「找不到问题了」——那句话在这一轮被推翻过两次，两次都是**换把尺子就又挖出东西**。

真正的信号是**信噪比翻转**：最后三把尺子里有两次「发现」其实是尺子自己的 bug
（孤儿扫描的正则把 `模块.名字` 的调用全排除掉；产物图的写关键词表漏了「输出」）。
**当误报开始多于真发现，继续造尺子的成本就高于它的期望产出了。**
