# 并行分派出去的时候：四件各自都真发生过的事

从 `AGENTS.md`「并行分派出去的时候」搬来（2026-10-13 落盘）。
搬走的理由与别处一样：`AGENTS.md` 要塞得进最紧那道静默截断，而**规则句一律留在原处**，
这里只放量出这些规则背后的经过。

## 一、分派提示自己不能自相矛盾

同一段话里既说「这一维留空、`score.py` 会现算」，又要它「顺便报一个综合分」——
它报的那个不是最终值。合并后 `score.py` 把分改了，`rank_breakdown.依据`
那段散文就开始解释另一个数字，`audit_pipeline` 报「依据那段话说的不是现在这个分」，
要逐条回改。

**要么让它们自己算完整，要么就别向它们要那个数。**

## 二、闸门不许被下游收紧

用户把「可以考虑」那档改成也出话术之后，有��� worker 评估里已经判了 FLAG 而非 FAIL，
**却在话术闸门上又自己加了一道** ——等于把裁定退回旧规则，而且没有任何地方记着它这么做过。

**裁定改的是闸门；「我没把握」该写进评估的 FLAG 与「投前必问」，不是拦在闸门上。**

## 三、并行 worker 会撞目录名

实测一个 worker 把 `<公司>_<岗位>/` 里**别人**的 `posting.md` 覆盖了，
那份材料属于同一公司的另一条挂法。它自查发现并还原了，但**靠自查才发现**。

派活时必须写明：**动笔前 `Test-Path` 查目录在不在**，在就按重复挂牌或另起名字处理，
**绝不覆盖已有文件**。

## 四、共享文件只由一个写

`seen_jobs.json` 那一轮**不许 worker 碰**（它们只交自己的 JSON 片段，
写回由主会话统一、带版本戳地做）；`job_search_tracker.csv` 全程谁都别碰。

## 一次别派太多

实测一批 20 个里有 14 个只落了 `posting.md` 就算「成功」返回 ——
**worker 报 succeeded 不等于活干完了**，主会话必须自己核对目录里有没有
`evaluation.md` / `outreach.md`，别拿它的自述当交付。

这一条后来又兑现了一次：三个 worker 并行补材料，其中一个拿到的 URL 其实
盘上已有正本，它正确地判定「不用做」而一个字没改；另一个正确地认出
已有目录是**另一个岗**（同公司不同 JD）而没有覆盖。同一批里两种判断都对，
是因为提示里把「先查重、不覆盖」写成了硬约束。

## 五、worker 会清空共享的产物目录（2026-10-15）

上面第四节写的是「共享文件只由一个写」，指的是 `seen_jobs.json`。实测里折出的是
**另一种形状**：那轮 11 个打分 worker 把产物统一落在同一个临时目录，
其中一个建了个 `_scratch` 子目录暂存中间件，顺手把目录里**另外十份别的批次的
产物**删掉了。

十份里有一批是**已经落库**的，删掉只是白重做一遍；但如果那批还没落库，
**丢的就是没写回库的那部分工时**。而判据当时只盯 `seen_jobs.json`，
中间产物目录没人管。

> 规则补进 `AGENTS.md` 第 5 条：worker 只写自己那一个文件名，
> **不许清空、不许删改目录里的任何其它文件**。
>
> 派多批活时中间产物要**分目录**（每批一个 `out_xxx/`），不是分文件名——
> 同目录靠文件名互相认，本身就是给并行踩的坑。

## 六、「脚本跑过了」不等于「文件写出来了」（2026-10-15）

批次 01 的 worker 交上来一份 **382 行、逻辑完全正确**的生成脚本，
然后报告：「已写出 32,189 字节、校验 0 错」。回磁盘一看，`score_out/` 是空的——
**脚本它自己写完了，从没执行过**。它照着脚本的内容自述了结果。

后面几个 worker 大多正常，但这一条逼我把验收写成硬要求：
**生成器 + 磁盘验证六项**（存在 / 无 BOM / 条数对得上 / `key`·`url` 与源逐字符相等 /
七道门齐全 / 全文件扫 `�` 为 0），**不许只看生成脚本打印了什么**。

> 它和上面「报 succeeded 不等于活干完了」是同一族，但更靠后一步：
> 那条查的是**目录里有没有文件**，这条查的是**文件是不是真的被写出来了**。
> 一个 worker 完全可能两样都「做完了」——脚本是它写的，校验它也真跑了，
> 只是跑在**还没落盘的那个对象**上。
>
> 判据：验证脚本必须 **`open(path)` 重新读**，在**字节层面**查。
> 对着内存里的对象验一遍等于没验。

## 七、主会话自己写的旁路脚本，判据照样被绕过去

2026-10-15 这一天三处都栽在同一件事上：**规则写在仓库里，我写的旁路代码没读它**。

- 按 URL 建映射写回 → 绕过了 `_cli.stable_id` 注释里写着的「同一 URL 可能挂两个岗」
  （详见下文「批量写回与批次编排」第二节）；
- 增量导出用已在用的批次文件名 → 绕过了「不覆盖已有文件」；
- 收尾拿 `_basis_is_stale` 的正则去猜哪几条依据过期 → 把一条其实自洽的存量判成了要改。

**旁路代码不读正本的注释，等于那条规则对它不存在。**
派 worker 和写自己的脚本，同一条判据都要落到**那一段代码**上，
而不只是「我读过、我知道」。

---

## 批量写回与批次编排：同一轮里连踩的四个

规则句在 `AGENTS.md`「并行分派出去的时候」那一段末尾（写回按 `key` 定址、粗筛不许覆盖深评、`--show` 不可当验证、增量导出只新增、阈值要有出处），
这里只放量出它们背后的经过，四件事按踩到的时间排。

## 一、`--import-from` 会「假成功」：缺 `title` 写进去就再也读不回来

并行抓 JD 的那个 worker 自己发现的，抓完 50 份智联的正文、导入时命令行打印
「收录：50 份」，**详情库容量一点没动**，`jd_store.py --show <url>` 回的是
「库里没有这份 JD 的正文」。

原因在 `jd_store.py`：`save()` 用 `stable_id(url, title)` 建键，而 `--show` / `status`
解析时 `title` 取自 `seen_jobs.json`。导入文件里没有 `title` 字段 → 键算成
「URL + 空标题」→ 与库里的键对不上 → 文件写进去了、`load()` 永远找不到它。
`import_dir()` **不校验 `title`**，所以这是静默失败。

`jd_store.py` 自己的 docstring 写着「最好有 `title`」——「最好」两个字既不是校验也不是报错，
读的人当成了建议。

> 修法：导入文件的 `title` 必须取自 `seen_jobs.json` 里**同一 URL 那条**的 `title`，
> 且 URL 与库里逐字符一致。导入后**必须验可读性**，不能只看「收录 N 份」：
> `python tools/jd_store.py --show <url>` 能打出正文，才算进去。

## 二、按 URL 建映射会把两个岗写成一个

我写的打分写回脚本第一版是 `by_url.setdefault(norm_url(e["url"]), k)` —— 即
**同一个 `norm_url` 只保留第一条**。

实测：`IT负责人`（key `jb4c2564e51`）与 `信息化负责人`（key `j1f54a3d5aa`）共用
`https://www.liepin.com/a/80501715.shtml`，是两个不同的岗、正文也不同。
写回时后者被 `setdefault` 吃掉，写到了前者身上——**前者的判词被静默覆盖**。

⚠️ 最难看的地方：`tools/_cli.py:stable_id` 的注释**早就写着这件事**
（「带上职位名是因为 51job 实测同一 URL 下挂着两个不同职位」）。
判据在仓库里，我写的旁路代码绕过了它。**旁路代码不读正本的注释，就等于没有这条规则。**

修法：按代理回传的 `key` 落；`url` 只在 key 对不上时做**逐字符相等**的兜底。
`norm_url` 只能显示和兜底，不能定址。

> 检出方法（可复用）：把同一 `norm_url` 的多条记录挑出来，比对它们的 `rank_breakdown`
> 是否**完全相同**——相同就说明互相覆盖过。实测 15 组重复链接里中招 1 组。

## 三、增量导出用了已在用的批次文件名

详情库抓回来的 JD 是**陆续**到齐的，所以要分批导出打分包。第一版增量导出从
`batch_09` 开始编号——而 `batch_09`/`batch_10` **当时已经有对应的批次在跑**。
于是包被覆盖，而 `score_out` 里同名的那份结果文件还是**旧批次**的：
名字对不上、内容张冠李戴。

> 代价不只是重打一遍：正在读那个文件的 worker 拿到的是另一批岗，
> 它的输出会和文件名声称的那批对不上。**这是并发下的静默错配**，
> 只有把每批产物逐条与源包 `key` diff 才看得出来。
>
> 修法：增量导出**只新增、绝不删改既有文件**，前缀带轮次（`batch_r2_*` / `batch_r3_*`）。

## 四、收尾时「依据」停在旧口径，分数却是新的

`writeback` 会把深评的**分数与判词**写回库里，但**那段解释散文不一定跟着换**。
于是总览页上用户读到的一段话在解释另一个数字——
`audit_pipeline` 报「依据那段话说的不是现在这个分」。

实测两类，一类是我的错、一类是工具的：

- **我的错**：一个 worker 写的依据说「专业能力 80、业务领域 45」（技能维 66），
  而它自己的评估文件里是 63。分数是 `score.py` 现算的（对），
  散文是粗筛那一版留下的（错）。
- **工具的假阳性**：`segment-行业市场专家` 那条其实自洽（41×0.4 + 50×0.267 + 30×0.333 ≈ 40），
  但依据里写了「技能维……41」，而检验器的正则
  `_cli.DIM_SAID = (技能|薪资|强度|发展)[^。；]{0,14}?(?:这一维|维)?[^。；]{0,6}?给\s*(\d{2})`
  把「技能维……给 25」（那 25 是**业务领域**）读成了技能维=25。

> 修法：把四个维度的数**在依据里直接写成「<维度名> <数>」**，
> 不要写成「技能维业务领域只给 25」这种把两个数挤在一句里的形状——
> **那一句人读得懂，检验器读不对。**
>
> 另一条：判不出写不写得出时，**别拿正则去猜**。`_basis_is_stale` 的判据是
> 「依据里点名某维给了多少分，而库里不是」，形状对不上时它会误报；
> 拿它当唯一判据就会去改一堆其实没问题的存量。

## 五、职位名带不带薪资串，决定了去重键 —— 同一个岗会被收两次

2026-10-15 补记。抓 BOSS 那批时 worker 报了一件事：它导入的两份「新增」其实**库里已经有了**。
顺着查下去：**同一个 URL 在 `seen_jobs.json` 里有 14 组多记录，其中 12 组是同一个岗**。

```
j373f8385c4 | '移动端产品经理（AI应用方向） 25-35K'   status=ranked
jf0c1824618 | '移动端产品经理（AI应用方向）'          status=new
```

去重键是 `<url>#<职位名>`，而**职位名有时带薪资串、有时不带**
（全库 81/1623 条带）——于是同一个岗拿到两个不同的 key，收成两条记录。

实测影响有两处，都不是「多一行」那么轻：

- **`--show <url>` 解析到哪一条是不确定的。** 它在 seen 里用 `next()` 找标题，
  同一个 URL 有两条时，**读到的是先出现的那条，不是你刚写的那条**。
  那个 worker 是靠「正文与库里那份逐字节相同」才确认自己写对了——
  **`--show` 在这种 URL 上根本不能当验证用。**
- **一半是 `ranked` 一半是 `new`。** `new` 的那条会被下一轮重新评一遍，
  同一个岗评两次、出两份材料。

`dupOf` 这个字段（全量 `0` 条在用）本来就是为了「同一个岗的重复挂法不重复跑」，
但它**在这两种标题形态面前认不出是同一个岗**，所以一条都没标上。

> 那 14 组里**只有 2 组是真不同岗**（猎聘把 `AI提效/AI落地` 和 `AI提效/AI落地-急`
> 挂同一个 URL；`IT负责人` 与 `信息化负责人` 也是同链接不同岗）——
> 那两条**不能合并**，正是 `stable_id` 带职位名的理由。
>
> 合并那 12 组是一次**数据迁移**：要同时改 `seen_jobs.json` 的状态、
> 材料目录的归属、详情库的键，**且不可逆**。所以不在任何一轮 auto 里自动做。
> 判据在 `AGENTS.md`「并行分派出去的时候」那一段的末尾。

## 七、批量写回脚本每轮重放全部批次 = 粗筛覆盖深评

2026-10-15 同一天栽的**最贵**一次，而且栽得很安静。

打分写回脚本（主会话自己写的，`apply_scores.py`）每跑一次就把 `score_out/` 里
**所有**批次重放一遍。这个设计在「一轮之内反复应用」时是对的——第一批、第二批依次落库，
重放幂等。

**但它跨轮就不幂等了。** 批次文件里存的是**当初的粗筛结果**；而深评是**后来**
由出材料的 worker 写盘、再由 `writeback.py` 从 `evaluation.md` 回写进库的。
两轮之间跑一次写回脚本，那批粗筛就把深评**盖回去了**。

实测被盖掉的三个：

| 岗 | 深评 | 被盖成粗筛 |
|---|---|---|
| 某财税科技公司 · AI智能体平台产品（Coze/WorkBuddy） | **77 值得投** | 81 **强匹配** |
| 某财税科技公司 · 同上·产品**总监** | **72 值得投** | 81 **强匹配** |
| 某大模型公司 · AI Coding 产品经理 | **71 值得投** | 74 |
| 某互联网大厂 · AI产品经理-ima.copilot | **70**（按本人裁定改过的那个数） | 63 |

> 危害不是「分数回退了」，是**判词从「值得投」升成了「强匹配」**——
> 一个粗筛乐观、深评谨慎的岗，就这么在面板上换了档。
> 依据那段散文也被换成了粗筛版，于是 `audit_pipeline` 报「依据说的不是现在这个分」。

修法（已加进脚本）：**写回时若该条 `rank_breakdown.来源` 以「深评」开头，跳过。**
深评是存档（`evaluation.md`）的派生物，`writeback.py` 才是它唯一的写入口。

> **判据：「批量重放」只在一个事实源上是幂等的。** 一旦同一个字段**有了第二个写入者**
> （这里就是 `writeback.py`），重放旧值就不再是幂等操作，而是**按时间倒流**。
>
> 更普适的一条：**脚本「每轮都跑一遍」的设计假设了库里只有一个写入者。**
> 出现第二个写入者时，必须显式判先后——判据是 `来源` 那样的**出处字段**，
> 不是「我这次要不要覆盖」。

## 八、导入门槛要用仓库的，别自己发明一个

2026-10-15 分派抓 JD 时，我在提示里写了「正文不足 **200** 字不收」。
仓库自己的门槛是 `tools/_cli.py` 的 **`JD_MIN_BODY = 80`**——
**200 是我从上一轮的临场判断里搬过来的，仓库里没有这条规则。**

代价是三条本该入库的 JD 被我挡掉了（51job 一条 189 字、BOSS 两条 173 / 163 字），
按工具的口径它们都够格。补进去之后待评队列少了三个。

> **提示里给出的阈值必须能在仓库里指出出处。** 指不出来的那就是执行者自己加的闸门——
> 而「闸门不许被下游收紧」那条规则同样适用于**主会话自己**加的闸门。


这一轮里 `score_out/` 被 worker 清空过（见 `parallel-dispatch.md` 第五节）。
当时 130 条结果**早已落进 `seen_jobs.json`**，所以没丢——但那是因为中间产物只是中转。

**判据：任何一轮的「已落库多少条」都要回库本身数**，不要拿临时目录的条数当交付。
库是事实源；中间文件随时可以被下一个 worker 删掉。
