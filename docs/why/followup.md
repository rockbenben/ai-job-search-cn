## 那个零为什么不该被拿来推一个动作

那个零本来就只是投递记录的零（国内回音基本走平台
站内信，这个工具一条都读不到），据它推一个动作等于拿一个读不全的数去指挥人。

## 名单见底时，补货优先于「先发」（2026-10-14 用户裁定）

> **「还有材料没投的时候也会先说去补货。这是正确的」**

## 上一条裁定旁边那句「有材料没发 → 先发」，加了一个前置判断

`AGENTS.md` 顶上写的是「有材料没发 → 先发；没有 → `/job-auto` 接着抓」。
用户这句话是冲着**同一个状态下两个出口的差别**说的：手上还有材料没投，
而面板在补货那一支里仍然先说去补货。

理由在 `build_dashboard.SHORTLIST_FLOOR` 那个常量的 docstring 里：
**补货的前置时间比名单见底的速度长**——手上只剩两三个能投的岗时，
先去跑一轮补货，投递才不会停摆；发完手上那几个再回来，正是下一次循环的事。
所以它不是推翻 2026-08-29 那条裁定，是给它加一个前置判断：
**「有材料没发」要先问「名单还够不够」**。够就照旧先发。

## 这一支本来只有面板有

面板那一支 2026-08-13 就有（`n_sellable < SHORTLIST_FLOOR` 那一支，
当时印的是 `/job-scrape`，同一天改成 `/job-auto`）。**终端自检没有**——
于是「手上 14 份材料没投、能投的只剩 3 个」这个状态下，面板说去补货、
自检说先把备好的发出去。

`tests/test_both_next_steps_agree.py` 顶上把这个形状记成「已经栽过两次」
（2026-08-13、2026-08-22），两次都是**「一条规则加在一个出口上，
另一个出口照旧」**。第三次是同形状的延续：这一支既没有落进正本，
也没有两个出口都实现。

接的时候有三处是「不接就等于没接」：

1. **两个数要一起给**。面板那一支按 `n_sellable` 与 `n_unranked` 分岔
   （有待评积压先去评库存，没有才去抓）。只给前一个，终端会在
   `/job-scrape` → `/job-scrape` 那个死循环上没有防护——
   新抓的没评分，`n_sellable` 永远是 0，于是每一轮都以为名单见底了。
2. **门槛数要有一份被钉住的副本**。`doctor` 不 import 仓库模块，
   `SHORTLIST_FLOOR` 只能持副本，相等由
   `tests/test_both_next_steps_agree.py` 里那一条钉住（同族：`QUIET_DAYS`、
   `AGENCY_WORDS`、`DATE_FORMATS`）。这个数比那三个更险一点：
   它决定的是「手上还有材料没投的时候，到底叫他先发还是先补」。
3. **那句「查不到就交回 None」的约定，两个出口都得认**。当成 0 就等于
   说「一个能投的都没有」——把手上 14 份备好的说成不必管。
   接这条约定时顺手逮到面板一个 `TypeError`：`next_step` 里
   `n_unranked > 0` 直接拿缺省值 `None` 比，**整个面板出不来**。
   现有两个调用方都传了数，所以它一直藏着。
