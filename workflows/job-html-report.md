# /job-html-report —— 投后分析报表：哪类岗回复率高、卡在哪一环

拿 `job_search_tracker.csv` 和 `documents/applications/` 下的投递归档，生成一份**自包含的 HTML 报表**。产物就是**一个 `.html` 文件**——不用起服务、没有任何依赖，浏览器直接打开就能看。

本命令里所有路径——输入和输出——都是**活动用户的**，即在 `users/<活动用户>/` 下（解析规则见 `AGENTS.md`「活动用户与多用户」）。**先读 `.active_user`**；缺失或为空就让用户去跑 `/job-setup` 或 `/job-user`，然后停。**这份报表只汇总一个人的投递——绝不许把 `users/` 下几个人的行合在一起。**

## Step 0：解析参数

- **没给任何参数** → 输出到活动用户的 `reports/application-dashboard.html`（即 `users/<活动用户>/reports/application-dashboard.html`）
- **给了一个路径**（例 `/job-html-report ~/Desktop/report.html`）→ **原样用那个路径**（那是他自己选的，可以在 `users/` 之外）
- 带 `--open` → 写完之后**你自己把它打开**：

  ```bash
  python -c "import pathlib,sys,webbrowser; webbrowser.open(pathlib.Path(sys.argv[1]).resolve().as_uri())" "<刚写出的路径>"
  ```

  跨平台（`webbrowser` 是标准库，`serve.py` 打开总览页用的就是它），零依赖。
  没有执行权限就开口要；真的要不到，再退回「告诉他路径」，并**说明是没能打开**。

  > ⚠️ **这一条原来写的是「写完之后告诉用户去打开这个文件（这条命令打不开浏览器）」。**
  > 而不带 `--open` 也会告诉他路径 —— 也就是说这个开关**什么都没改变**，
  > 而索引（同时是面板上那份帮助）承诺的是「**出完直接打开**」。
  > 一个点了没反应的开关，比没有这个开关更坏：用户会以为是自己敲错了。
  >
  > 修的是正文不是承诺，因为 `AGENTS.md`「有一件事不必回命令行」那一节
  > 立的就是这个立场：「**不要产出一个 HTML 再把路径贴给他让他双击**——
  > 新用户不知道该敲什么」。那条讲的是总览页，理由在这里一样成立。
  > （2026-09-02 通读时发现。）

活动用户的 `reports/` 不存在就先建出来。

## Step 1：收数据

并行读这几样：

1. **`job_search_tracker.csv`** —— 主数据源。每一行解析成一条记录，字段是：
   `date`, `company`, `sector`, `role`, `role_type`, `channel`, `status`, `contact_person`, `fit_rating`, `notes`, `cv_file`, `cover_letter_file`, `source`

   **文件不存在或零数据行时**（全新 clone 里它根本不存在——只有 `/job-outcome` 会创建它；
   跑过 `/job-scrape`、`/job-rank`、`/job-apply` 但还没投递过的用户就是这个状态）：**不要生成报表，
   也不要报错**。这是投**后**分析工具，没有投递记录时它没有可分析的对象。直接说：

   > 还没有投递记录（`job_search_tracker.csv` 不存在或为空）。`/job-html-report` 分析的是
   > 投递之后的结果，请先用 `/job-outcome <公司>` 记一笔投递记录。想看投递**前**的流水线状态
   > （抓取/排名/材料），跑 `/job-dashboard`。

   然后**停止**——不要写出一个全零的报表文件，那会让用户以为流水线出了问题。
   **绝不**为了「让报表有内容」去读 `seen_jobs.json` 里的未投职位充数：本命令只统计
   已投递的记录，混入未投职位会让漏斗率与拒绝率全部失真。

2. **`documents/applications/*/job-outcome.md`** —— 每一次已结案的投递都读一下它的归档，取出**实际走到了哪几轮**（那些勾选框）和备注。按「公司 + 岗位」模糊匹配（转小写、忽略标点）并进对应的那一行投递记录。**某一行有归档但匹配不上时，照样把它作为额外上下文附上。**

3. **`job_scraper/seen_jobs.json`** —— **补两样：行业，和「谁在招」。** 台账的
   `sector` 那一列永远是空的（判据见 Step 2「按行业」），行业得按 `source` 链接
   回查这里的 `compIndustry`；同一次回查顺手取 `isHeadhunter`（判据走
   `_cli.via_headhunter`，**别自己认字段名**——它驼峰/下划线两种写法都吃过亏）。**只读这一个文件**：`job_scraper/details/*.json` 里也有同名字段，
   但实测它对台账那批一条都补不出来（91% 的行业在 `seen_jobs.json` 里，
   `details/` 只有 8%），多读一遍没有收益。
   这个文件不存在（还没抓过岗）→ 行业整列按「未标注行业」处理，**不报错**：
   投递记录可以是用户手写的，没有职位库照样出报表。
   ⚠️ **和上面第 1 条那句「绝不读 `seen_jobs.json` 充数」不冲突，但两条必须一起读。**
   那一条禁的是**拿未投的职位当记录**（会让漏斗率与拒绝率失真）；这一条只是拿台账
   **已有的那一行**的 `source` 去查一个字段。判据一句话：**行数只由台账决定，
   职位库一行都加不进来。** 查不到就是「未标注行业」，不许因此少一行、也不许多一行。

**状态归一** —— 算统计之前，先把投递记录里的取值映射成五个标准桶。
**桶名（左）是内部键，只用来算数；括号里的中文才是画到页面上的字。**

| 内部键 | 归入的 tracker 值 | **页面上显示** |
|---|---|---|
| `active` | `applied` | **已投递** |
| `interview` | `interview` | **面试中** |
| `offer` | `offer` | **拿到 offer** |
| `hired` | `hired` | **入职了** |
| `closed` | `rejected` / `no response` / `no_response` / `offer declined` / `offer_declined` / `interview_only` / `withdrawn` | **挂了 / 没下文** |

⚠️ **这份报表是给中文求职者看的，界面上一个英文标签都不该有。**
`job_search_tracker.csv` 的 `status` 列存的是 `applied` / `interview` 这样的英文码
（统计要用，不能改），但**那是内部码，不是给人读的字**——`tools/tracker.py` 顶上
那段注释写明了这条分界，并点名 `/job-html-report` 是它的消费方之一。
**中文说法有两套，各有各的场合，都别另造第三个：**

- **数状态（本报表的桶、漏斗计数）** → 用总览页漏斗那套：`材料就绪` / `已投递` /
  `面试中`；再往后的 `拿到 offer` / `入职了` / `挂了` / `没下文` 取 `tracker.LABEL`。
- **记动作（按钮上的字）** → 用 `tools/tracker.py` 的 `LABEL`：`我投了` / `约面了` /
  `挂了` / `没下文` / `拿到 offer` / `入职了` / `我拒了`。**这一行是按钮词表，
  照 `LABEL` 抄，别按上一行的桶名改**（我自己在批量替换时就把它改错过一次）。

这张表原来把 `applied` 写成「**等回音**」——那个词在总览页和 `tools/` 里**一次都没出现过**，
是这份文档自己造的第三套说法；而它下面就写着「同一个状态在总览页和这份报表里必须是
同一个词」。同一段里自相矛盾。

## Step 2：算汇总统计

从规整后的数据算出这些：

- **投递总数**
- **按状态桶：** 每个桶各有几条
- **按行业：** 每个行业各有几条。取 `sector` 那一列，**取不到就从职位库推**——
  拿这一行的 `source` 链接去 `seen_jobs.json` 里认那个岗，取它的 `compIndustry`。
  ⚠️ **`sector` 实际上永远是空的。** `tools/tracker.py` 的 `set_status` 明写着
  「sector / role_type / channel 留空——**不猜**」，而它是台账唯一的写入方；
  除了用户自己往 CSV 里手填，没有第二条路。实测活动用户 2026-08-23：85 行里
  `sector` 非空 **0** 行，而按 `source` 回查职位库能补出 **62** 行、29 个行业。
  照旧只读那一列的话，条形图、行业下拉、表格里那一列会**同时**变成一片空白——
  而「哪类岗回复率高」就是本命令标题里的那半句。
  这跟下面「按渠道」那条是同一种办法：**读时推导，不写回台账**。写回去就违反了
  `set_status` 那条决定（台账是给人回看的，填一个「大概是这个行业」进去，
  下次校准就按它算了）；读时推导只影响这一张报表，不落盘。
  **补不出来的那些归到「未标注行业」单独一档**，别丢掉——丢掉会让这一组的合计
  小于投递总数（同 `gate_fail_tally` 的「没说是哪道」：数据缺口要露出来，
  不许并进别的档）。
- **按渠道：** 按 `channel` 那一列的**平台名**分组（猎聘 / BOSS 直聘 / 智联招聘 /
  前程无忧…），取不到就从 `source` 的链接推（`tracker.channel_of`）。
  ⚠️ **这里原来写的是「网申 / 内推 / 其它」**——那是**投递方式**的分类，
  而这一列存的是**平台**，两套东西。方式没有任何地方在记（`内推` 只有用户
  自己往那一列写才会出现），照旧写的话图例承诺了一套、柱子画的是另一套。
- **按谁在招：猎头代招 vs 企业直招 vs 判不出。** 判据走 `_cli.via_headhunter`
  （`None` 单独一档，别并进「直招」——没判过不是「不是猎头」）。

  > ⚠️ **这一档不是「又一个分组」，它决定上面那两个率该怎么读。**
  >
  > 总览页为这件事修过一次，理由抄在这儿（`build_dashboard.py` 里那段「投了 N 个 0 回音」的说明）：
  > 「『投了 N 个 0 回音，去审简历』这句话的分量，完全取决于 N 里有多少是猎头
  > 代招。简历投给猎头是先进他的库，推不推、什么时候推由他定，岗位可能早就
  > 关了 —— **那批的沉默是渠道的事，怪不到简历头上**。」实测 2026-08-24 当时 54 个已决出
  > 结果里 32 个是猎头代招，**59% 的样本根本不构成简历的证据，而按它去改简历
  > 是照着错的诊断动刀**。
  >
  > 而这份报表的标题就是「哪类岗回复率高、卡在哪一环」——**它此前全文一次都
  > 没提过猎头和直招**（实测 2026-08-24，`猎头` / `直招` 均 0 命中），
  > 一个整体回复率印出来，读者只能得出那个被修掉的结论。
  >
  > 所以：**漏斗转化率与拒绝率要在企业直招那一组上再算一遍**，并把两个数并排
  > 摆出来（整体 / 直招）。整体那个数留着，但它不是用来下简历结论的那个。
  >
  > 直招那一组样本太小时（`< 20`，判据同 `build_dashboard.NO_REPLY_ALARM`
  > 的三倍法则）→ 写「直招只有 N 个，还不够下结论」，**不要印一个率**。

- **按年份/季度：** 按 `date` 字段分组（它可能只是个年份如 `2025`，也可能是完整日期）
- **漏斗转化率：** 有百分之多少过了简历关（走到面试或更后面）
- **拒绝率：** 已拒/已关 ÷ 已结案的总数（**不算还在跑的**）

**分母为零时不要算成 0%。** 只有「已投递」的行（都还没有结果）时，「拒绝率」的分母是 0；
漏斗率同理。这种情况一律显示 **「暂无（尚无已解决的投递）」**，不要渲染 `0%`——
`0%` 读起来像「一个都没被拒」，那是个假的好消息。同理，某个分组（行业/渠道/年份）
只有 1 条记录时照常展示计数，但**不要**给它算百分比。

**分母不为零、但多数还在等待窗口内时，同样不给这两个率。** 这一条和上一条治的
不是一件事：上一条是「没有分母」，这一条是「分母有，可它还没到该有结果的时候」。

> 判据与总览页共用一条（`export_web_data` 的 `too_early`）：
> **一个回音都没有，而「还在等」的超过总数一半** → 两个率都显示「还没有」，
> 不渲染 `0%`。实测活动用户 2026-08-21：85 个投出去、66 个还在等（中位已等 9 天，
> 静默线 10 天）—— 印一个大号「有回音 0%」，读者看到的是「市场把你全拒了」，
> 而实际是近八成**还没到该回的时候**。
>
> ⚠️ **判据是「还在等的占多数」，不是「有一个在等」。** 写成「只要有人在等就藏」
> 的话，199 个已读不回加 1 个昨天刚投也会把两个率一起吞掉 —— 那时 0% 是真的，
> 藏起来是另一个方向的谎。
>
> 「还在等」按静默线判（`followups.QUIET_DAYS`，10 天），别在这里另定一个数。

## Step 3：生成 HTML

写出**一个自包含的 HTML 文件**。CSS 全部内联在 `<style>` 里，JS 全部内联在 `<script>` 里。环形图和柱状图都**手写内联 SVG**——不用图表库、不用 CDN、**不许有任何外部依赖**。**这份报表每次打开都必须能完全离线渲染。**

**转义（必做）：** 从 CSV 或归档文件里读出来的**每一个值**，写进页面之前都要做 HTML 转义（`&` `<` `>` `"` `'`）——**包括表格单元格、被截断备注的 `title` 属性、以及放进 SVG 里的任何文字**（`<text>` 标签、图表提示）。从职位描述里抄来的备注和公司名经常带着这些字符；不转义就会**把版面顶坏，或者把标记注入到一个用户常开的页面里**。

### 设计规格

- **配色：** 用 CSS 自定义属性。状态色：
  - Active: `#3b82f6` (blue)
  - Interview: `#f59e0b` (amber)
  - Offer: `#8b5cf6` (purple)
  - Hired: `#22c55e` (green)
  - Rejected/Closed: `#ef4444` (red)
- **字体：** system-ui 字体栈，**不引网络字体**
- **数字卡片：** 白底、淡投影、大号粗体数字、标签在下面、左侧一道状态色的边
- **图表：** 宽屏排成两列网格，窄屏堆成一列
- **表格：**
  - 隔行浅底
  - 状态那一列用带色的小标签
  - `source` 那一列，值是链接（`http` 开头）时渲染成超链接
  - 空单元格渲染成 `—`
  - **前端筛选**：一个文本框按「公司 + 岗位 + 行业」过滤；状态与行业各一个下拉独立过滤；**三者是且的关系**
  - 默认**最新的排最前**（按 `date` 降序，再按公司名排）
- **自适应：** 900px 以上好用，更窄也不能垮
- **页脚：**「由 ai-job-search 生成 · {ISO 日期}」（页脚也是页面上的字，写中文）。
  **不要写死某个 AI 工具的名字**——这份报表由谁跑就由谁生成，写「由 Claude Code 生成」
  在 Codex CLI 或 Qwen Code 下跑出来就是假的。工具名只属于 `AGENTS.md` 的能力对照表。

### 图表（内联 SVG）

图表上方的 `<h3>` 标题就取下面这几个**中文名**：

1. **状态分布**（环形）—— 每个状态桶一片，颜色取上面的调色板
2. **按行业**（横向条形）—— 判据同上（Step 2「按行业」：`sector` 取不到就按
   `source` 回查 `compIndustry`，补不出来的进「未标注行业」），降序
   ⚠️ 这里原来写的是「每个行业的**公司数**」，而 Step 2 数的是**记录数**——
   同一张图，两个数。实测活动用户 2026-08-23：30 个行业里 5 个两数不同，
   合计 **85 条 vs 77 家**，也就是这张图的合计会比同一页上的「投递总数」少 8。
   本报表其余每一张图（状态分布 / 按渠道 / 漏斗）数的都是记录，行业这张跟着来。
   隔壁「按渠道」写的就是「判据同上」——**图表这一节只说画法，判据一律回 Step 2 拿**，
   在这儿复述一遍就是等着它们各长各的。
3. **按渠道**（条形）—— 按平台分组（判据同上：`channel` 列，取不到就从链接推）
4. **谁在招**（条形）—— 猎头代招 / 企业直招 / 判不出，判据同上（Step 2「按谁在招」）。
   **这张图要紧挨着漏斗那张放**：漏斗里那个整体转化率该怎么读，取决于这张图的构成
   （理由见 Step 2 那一段）。
5. **投递漏斗**（横向条形）—— 已投递 → 面试中 → 拿到 offer → 入职了，每根条 = 走到这一步的数量
   （**漏斗用「已投递」不是「我投了」**：前者是数状态、后者是按钮上记动作的字，见上面那两套词汇）

   ⚠️ **这一张是累计口径，Step 2 那张归一表不是——中间要换一次算法。**

   归一表是**互斥**的：一个走到 offer 的岗只落进 `offer` 那一格。照它直接画，
   「已投递」那根条就只剩**还停在已投递的那些**，「面试中」不含已经拿到 offer 的——
   每一格都比真的少，而且漏斗会不再逐级递减。**「走到这一步的数量」是累计**：

   | 这根条 | 数哪些行 |
   |---|---|
   | 已投递 | **全部**投递行（走到后面几步的也走过这一步） |
   | 面试中 | `interview` / `offer` / `hired` |
   | 拿到 offer | `offer` / `hired` |
   | 入职了 | `hired` |

   判据与总览页那条漏斗同源（`export_web_data.funnels_of`，它的注释原话是
   「这里是**累计口径**：一个岗可以同时在『已投递』和『面试中』里」）；
   「面试中」那一格的成员取 `build_dashboard._INTERVIEW_STATUSES`，
   **别在这里另列一份**。
   **两块屏幕上「面试中」是同一个词，就必须是同一个数。**

   > ⚠️ **`interview_only` 不进这一格**，尽管它字面上是面过。正本没收它，
   > 这里就不能收——**这一条的全部意义是两边同一个数**，为了「更合理」
   > 单方面多收一个状态，正是它要防的那件事。觉得正本收窄了就去改正本，
   > 两边一起变。（`outcome_stats` 把 `interview_only` 算进「约面或更远」是
   > 另一根轴：那张表问的是**有没有回音**，不是**走到了哪一步**。）

   > 互斥的地方只有**状态分布那张环形图**——饼图的片本来就该互不重叠，
   > 那张照 Step 2 的归一表画是对的。别把这条推广过去。
   >
   > 这两句原来一处写「互斥五桶」、一处写「走到这一步的数量」，同一个文件里
   > 隔着一百多行，中间没有任何一步做转换。实测 2026-08-27 当时没显形
   > （88 行里 87 个还停在「已投递」，两种算法只差 1）——**它要等到真有人
   > 走到面试才露出来，而那正是这张报表最有用的时候。**

每张图都**手写成一个 `<svg>`**：拿 Step 2 算出来的统计值算好柱长与环形弧角，直接输出 `<rect>`/`<path>`/`<circle>` 和 `<text>` 元素——**不用图表库，也不用 `<canvas>`**。每个 `<svg>` 都要有 `role="img"` 和一句概括这张图的 `aria-label`，**同样写中文**（例如「状态分布：3 个已投递、2 个面试中、1 个拿到 offer」）——读屏用户听到的也该是中文。每张图外面包一个 `<div class="chart-card">`，上方配一个 `<h3>` 标题。**画进 `<text>` 节点的任何标签或数值，都要照上面那条规矩转义。**

### 表格：要有哪几列

表头写中文：`日期` · `公司` · `岗位` · `行业` · `渠道` · `状态` · `备注`（超过 80 字截断，`title` 里放全文） · `来源`（是链接就渲染成链接，否则 `—`）

**列名不要用 CSV 的英文字段名。** `date` / `company` 是文件里的列，不是给人看的表头。

某一列在所有行里都是空的，可以整列省掉。

## 设计原则

- **自包含。** 一个文件，完全离线——图表是内联 SVG，**不用 CDN、不发任何外部请求**。
- **只读不写。** 这条命令只负责读和渲染；**它从不往投递记录或归档里写任何东西。**
- **重复跑不出乱子。** 再跑一次就覆盖同一路径下那份旧报表——**不会越堆越多**。
- **数据少也要好看。** 只有几行时（现在就是），图表在小样本下照样画对；**这时表格才是主要价值**。**不要因为 N 小就把图表藏起来。**
- **绝不编造。** 报表里每一个数字都**直接来自** CSV 或归档文件。**缺的字段不许推断，也不许估算。**
