# /job-scrape —— 抓新岗并自动评分：各平台去重收集，抓完直接排出可以投的

本工作流里所有个人数据路径——`profile/search-queries.md`、`job_scraper/seen_jobs.json`、`job_search_tracker.csv`——都是**活动用户的**，即在 `users/<活动用户>/` 下（解析规则见 `AGENTS.md`「活动用户与多用户」）。**先读 `.active_user`**；缺失或为空就让用户去跑 `/job-setup`（第一个用户）或 `/job-user`（切换），然后停。框架自带的 `workflows/reference/search-queries.md` 是**共享的结构模板**，就放在原处——**绝不要把它和活动用户真正的查询词搞混**。（它以前放在 Claude 的技能目录里；正文搬走之后那句话**当时**仍然指着那儿，也就是指向一个已经不存在的文件——而对非 Claude 的工具来说，「技能目录」这个概念压根不存在。）

---

## 它怎么工作

拿用户资料里的搜索词，用 `.agents/skills/` 下**已装的各渠道搜索 CLI** 去招聘网站搜岗
（都够不着时退到网络搜索兜底）。搜到的跟**已经见过的岗**和**投递记录**去一遍重，
剩下的新岗带一个快速匹配判断摆出来。

## 怎么触发

用户说这类话就触发它：
- 「找新职位」
- 「搜一下岗位」
- 「有新岗吗」
- `/job-scrape`

可选参数：
- 一个方向词，只抓这个方向，例：`/job-scrape 数据科学`、`/job-scrape 解决方案`。
  **举例跟着活动用户的资料走**，不要写死某个行业——这个工具与行业无关，
  方向词从 `profile/candidate.md` 的目标岗位里取（原来这里写的是
  "data science" / "geophysics"，是这套工具最早那个用户留下的，与本仓库无关）
- `broad` —— **连实测已挖空、已判低效的词也重跑一遍**，例：`/job-scrape broad`。
  「跑全部分类」已经是默认了，`broad` 现在只多这一件事：绕过剪枝。
  隔了一阵、或市场有变化时用它复查
- `--no-rank` —— **只抓不评**。这条路要**自己收尾**：跑一次
  `python tools/export_web_data.py` 刷新面板，否则用户打开总览页看到的是抓之前的状态。

  > 默认那条不用管——它接着跑 `/job-rank`，刷新在那边做了。
  > 但**刷新是搭在转手上的**，`--no-rank` 一加转手就没了，收尾也跟着没了
  > （2026-08-13 全面检查命令逻辑时扫出来：会写盘的命令里只有它和 `/job-reset`
  > 收尾不刷面板）。默认抓完直接接 `/job-rank --auto`（见 Step 5.5），
  因为「待评的岗」不是可用产物。只想看看市面上有什么、不想等评分时才加这个
- `--no-browser` —— **这一轮不碰要登录的那三家**（BOSS / 智联 / 前程），只跑免登录的猎聘。
  面板上的勾选是长期开关，这一面旗子是**临时**的：不想改勾选、只想这一趟别动
  登录态账号时用它。例：`/job-scrape --no-browser`。

  > 这条原来**只写在 Step 0.4 的散文里**（「要临时不碰登录态账号用 `--no-browser`」），
  > 参数表和 `AGENTS.md` 的索引表都没有它 —— 而索引表就是面板上那份帮助的正文。
  > 教了怎么用、却没有一处列得出来，等于只有读到那一段的人才知道它存在。
  > 同层的 `--browser-scrape` 仍然收，但已经是默认行为，给不给都一样（同 Step 0.4）。

- `health` —— **只体检各渠道通不通**（Step 4.75），不搜岗、不去重、不出名单。例：`/job-scrape health`；`/job-scrape health liepin-search` 只探这一家，**哪怕它的开关是关着的**

## 执行步骤

### Step 0：把状态读进来

1. 读 `job_scraper/seen_jobs.json`（没有就新建，初值 `{"seen": {}}`）
2. 读 `job_search_tracker.csv`，把**已经投过的公司 + 岗位**取出来。文件不存在（刚 clone 下来——只有 `/job-outcome` 会创建它）时，**当成一次都没投过**（排除集为空）继续往下走，与上面 `seen_jobs.json` 的「没有就新建」同理。
3. 读 `profile/search-queries.md`，拿**这个用户自己的**搜索词。它不存在（说明用户还没跑过 `/job-setup`）就让他先跑 `/job-setup`。**这一步只要这一样**（判据 `doctor.profile_gaps(udir, "scrape")` 的 `block`）——`candidate.md` 里别的节还是占位符不挡抓岗，那正是 `/job-setup` 第一轮说完「够搜岗了」的意思；规则见 `AGENTS.md`「资料没填完是分档的，不是一个整体判断」。框架自带的 `workflows/reference/search-queries.md` **只是结构与策略参考**——里面的 `[QUERY_N]` 是占位符，**不是能跑的查询词**。

### Step 0.4：哪些招聘网站开着（面板上勾的那几个）

```bash
cat users/<活动用户>/job_scraper/portals.json   # 缺文件 = 四家全开
```

`{"猎聘": true, "BOSS": true, "智联": true, "前程无忧": false}` —— **关掉的整家跳过**，
并在 Step 5 的覆盖报告里单列一行「你把它关了」，别让用户以为是抓失败了。

> **这个开关在总览页上**（「从哪些招聘网站找岗」那一块，勾选框直接写盘）。
> 它落在盘上而不是浏览器里，就是为了让这一步读得到——存进 localStorage 的话，
> 命令行侧的抓取根本看不见它，那个勾选框就成了纯装饰。
>
> 与 `SKILL.md` 的 `enabled: false` 是两个东西，**两个都要开才抓**：
> 那一个是 fork 维护者「这个渠道我不装」，这一个是用户「这一轮我不想抓它」。
> 前者按渠道目录，后者按平台名。

**这个勾选是唯一开关**（2026-08-19 本人裁定「默认应该是勾选」）。原来它和
`--browser-scrape` 是**与**的关系——浏览器那三家要两个条件都满足才抓，于是用户
在面板上把四家都勾上、命令行侧却仍然只跑猎聘：**勾选框只有否决权、没有启动权，
而没有任何地方告诉他还差一个 flag**。实测代价是全库 85% 的岗来自猎聘，
命中率最高的 BOSS（13.5%）只抓到 126 个。

现在：勾着的就抓，取消勾选的整家跳过。要临时不碰登录态账号用 `--no-browser`；
`--browser-scrape` 仍然收，但已经是默认行为，给不给都一样。
账号风险改由下一步的额度闸门管。

**开抓前先看一眼有没有把大头关掉。**

```bash
python tools/portal_budget.py | grep 关掉    # 关着的那家行尾有「← 你在总览页关掉了这家」
```

勾选框是唯一开关，而**多数人关掉一家是因为当时撞了风控**——拦解了平台不通知，
勾就一直关着。实测活动用户 2026-08-23：猎聘勾是关的、`blocked` 已经是 false，
而它占语料 **85%**（2232/2638），四家里唯一还在产可投岗的也是它
（可投 8，其余三家合计 1）。这一轮补货照常跑，两轮零新增就触发停手条件，
报告写「挖不动了」——**而矿根本没开**。

上面那行有输出 → 在进度行里说一句，让他去面板勾回来；
他不勾就照常跑，别替他开（勾选框是他的）。

> ⚠️ **那个标记在行尾，别裸眼扫。** 这里原来写的是「关着的那家会写
> 『关着（额度没问题）』」—— 而工具**从来不印那句话**：2026-08-23 试过把第一列
> 改成那个写法，同日又改回去了（理由见 `portal_budget.py` 那段注释），
> 落地的是行尾一个 `← 你在总览页关掉了这家`，而那一行有一百多字，
> 前面还压着额度与冷却的说明。
>
> 实测代价（2026-08-24，就是这条流程自己）：执行者读了这份输出、报了
> 「四家额度全清」，**整趟跑完一次都没提猎聘的勾是关的** —— 而它占语料 85%。
> 报告写的是「补货这一轮跑不了（CLI 在冷却）」，漏掉了另一半原因。
> 正是上面那段自己预言的「报告写『挖不动了』，而矿根本没开」。
>
> 所以这一步**用 `grep` 过，不用眼睛过**：有输出就说一句，没输出就没这回事。

> 这一步原来只写在 `job-auto.md` 的补货节里——而单独跑 `/job-scrape` 的人
> 根本看不到它。2026-08-25 收口（抓取规则只留一处）时归位到这里。

### Step 0.43：被封的家，**勾着也不抓**

**优先级：封 > 勾。** 面板勾选回答的是「我想不想抓这家」，风控冷却回答的是
「现在允不允许抓」——**后者赢**。而且**封了就一直封着，不会到点自己解开**：
只有你确认外面那件事已经变了、亲手放行，它才继续。

```bash
python tools/portal_budget.py --check <渠道名>   # 退出码 1 → 这一条跳过
python tools/portal_budget.py --clear <渠道名>   # 你处理完了，放行
```

- 停着的通道：**一次请求都不发**，在覆盖报告里单列「被平台拦着，等你处理」。
- 放行只有一条路，而且**必须是人**：面板告警条上点那个按钮
  （浏览器那条写「我处理好了，恢复抓取」，CLI 那条写「我换好 IP 了，继续抓」），
  或终端 `python tools/portal_budget.py --clear <渠道名>`。**工具永远不自动解。**

> ⚠️ **这一段 2026-08-26 改回来了，而且是第三次翻面 —— 值得记全。**
>
> - 最早写的是「只有用户手动解封才恢复，不会到点自动放行」；
> - 2026-08-25 发现它和代码相反（`_one_lane` 一直是 `if now >= t:
>   return NOT_BLOCKED`），于是**把文档改成迁就代码**：「24 小时满了自动放行」。
>   那次只核了「文档和代码对不对得上」，没核**哪一边才是对的**；
> - 2026-08-26 本人裁定：「cli 被封后……只有用户手动点继续 cli 后，
>   才能继续 cli」。于是删掉自动到期那一行代码，文档回到最早那句。
>
> 三次翻面里最贵的是第二次：它把一条**正确的规则**改成了错的，理由只是
> 「代码是这么写的」。同一条矛盾当时两边各有一条测试钉着，所以它
> 两边全绿地活了一周 —— 不是没人查，是两个查的人各查各的一半。

> **探一次不许把起点推到现在。** 想确认恢复没有，最顺手的动作是再 `--block`
> 一次记一笔 —— 而那会把「已经封了多久」当场归零，屏幕上从「已经封了 16 小时」
> 变回「刚停」，读的人以为是自己刚撞封的。`block()` 对已经停着的通道**只更新
> 原因、不动起算时刻**（`test_reblocking_does_not_restart_the_clock` 钉着）。
> 这条规则 2026-08-25 就写下了，当时的说法是「不会把冷却从头再算」——
> 冷却没有了，它要守的那件事还在。

> **为什么解封必须归人**（2026-08-19 本人裁定：「显示封了的时候就应该停止 24 小时，
> 除非手动点击解封。否则 24 小时内，即使勾选了平台，也不该使用」）：
> 解封的前提是**外面那件事真的变了**，而工具两件都看不见：
>
> - **浏览器那条**要他本人去过一次验证（短信、滑块、联系客服），过没过完只有他知道；
> - **CLI 那条**要他换掉这个网络出口的 IP —— 限的是 IP，不是账号。
>
> 按时间自动解等于替他赌平台自己消气了。当天的实测是它没有，而且一次比一次重：
> **限流 → 账号标记异常（要短信验证）→ IP 被拦截**；08-24、08-25 又各撞一次，
> 第二次就是冷却刚过撞的 —— 到点换的还是同一个 IP。

### Step 0.44：一家同时只走一条通道，但**闸门放行的通道都要抓**

**抓取按渠道枚举，不按平台枚举。** 而这一轮到底枚举出哪几条，**不要自己拼**：

```bash
python tools/portal_budget.py --round     # 这一轮该跑的通道，一行一条
```

它把「勾着的家」和「闸门放行的通道」两件事一次算完，逐条给出结论，
并在主通道被挡住时明写「一家的主通道被挡住 ≠ 这一轮没有这家」。
**照这张单子跑，✓ 的每一条都要跑。**

> **为什么要有这条命令。** 下面那张表连同三处交叉引用、两段实测代价，
> 已经把规则写得很全了 —— 而 2026-08-30 还是整轮漏掉了 `liepin-browser`：
> CLI 撞限流那天它 0 次查询，而猎聘占这个职位库语料的大头。
> **2026-08-25 犯过同一个错，用户当场纠正过。**
>
> 差的不是规则。闸门按**通道**判，而人（和执行者）按**家**想 ——
> 「猎聘 CLI 停着」被读成「这一轮没有猎聘」。要把两个粒度对上，得逐条跑
> `--check`、再和 `portals.json` 交叉一遍：**五次查询加一次交叉引用，
> 全是机械活，而机械活交给人就会漏。**
>
> 下面这张表留着 —— 它答的是**为什么**（哪条是首选、为什么不双通道走）。
> 单子答的是**这一轮跑哪几条**。两件事。

渠道一共 **5 条**，每一轮照下表逐行走：勾着的、闸门放行的就抓。
**只有勾选关掉或闸门挡下的才跳过** ——「这条通道平时不是主力」不是跳过的理由。

| # | 平台 | 通道 | `--check` 用的名字 | 这一轮走不走 |
|---|---|---|---|---|
| 1 | 猎聘 | CLI（免登录接口） | `liepin-search` | 放行就走，**猎聘的首选** |
| 2 | 猎聘 | 浏览器 | `liepin-browser` | **只在 1 被闸门挡住时**走（自动降速：间隔 ×3）。1 能走就不走它——同一家不双通道 |
| 3 | BOSS | 浏览器 | `BOSS` | 放行就走（这家只有这条路） |
| 4 | 智联 | 浏览器 | `智联` | 放行就走（这家只有这条路） |
| 5 | 前程无忧 | 浏览器 | `前程无忧` | 放行就走（这家只有这条路） |

**一轮正常要动 4 条**（1 或 2 选一，加 3、4、5）。收尾报告里 5 行都要交代：
抓了的报抓了多少，跳过的报被谁挡的（勾选/冷却/额度），**少一行就是漏了一条渠道**
——2026-08-25 漏的正是第 2 行，代价见下面那段实测。

**同一家网站不要同时用两条通道抓**——那是把这个账号的暴露量翻倍，而拿到的岗高度重合。
但「不同时」不等于「主通道一停这家就整个没了」：**这一轮走哪条由闸门定，
不由通道的名分定。**

- **猎聘：CLI 优先**（`liepin-search` 免登录、不碰账号，字段最全，容量也够）。
  **CLI 被闸门挡住时，浏览器那条照常进这一轮**，按闸门自动给的降速额度走
  （间隔 ×3）。那不是「启用后备」，那就是下面那张不对称表的正常执行。
- **BOSS / 智联 / 前程无忧：只有浏览器一条路**（三家都没有可用的免登录 API，
  见本文件顶部的实测），所以不存在选哪条的问题。

> ⚠️ **这一条 2026-08-25 推翻重写。** 原文是「猎聘的浏览器路径**不进常规轮次**，
> 只在 CLI **长期**不可用时才启用（接口改了、CLI 装不上、`bun` 不在）——那是
> 『CLI 这条路没了』，不是『这次被限流了』」。
>
> 它和三处同时打架，而且打的是同一个点：
>
> - `cdp-portals.md`「三条从这张表读出来的结论」第 1 条：**「猎聘 CLI 限流 ≠
>   这一轮没有猎聘」**，并实测浏览器容量更大（21 页 × 42 条 vs CLI 10 页 × 20 条）；
> - `portal_budget.py` 的实现：CLI 冷却时 `--check liepin-browser` **放行**，只降速；
> - 本文件 Step 0.46 已经写着「跳的是通道，不是整家……CLI 冷却时它按放慢后的间隔照跑」。
>
> **三处对、一处错，而错的那处在最前面。** 实测代价（2026-08-25 一次 `/job-auto`）：
> 补 JD 时 CLI 第一个请求就 `RATE_LIMITED`，执行者照这一行把**整个猎聘**跳过，
> 报告写成「CLI 在冷却，明天再说」——用户当场纠正「CLI 停了不要紧，你可以用浏览器的啊」。
> 补跑的结果：**猎聘浏览器搜一页 40 张卡、新增 36 个**，而同一天 BOSS、智联、
> 前程无忧三家各跑了 1-2 轮，合计才 50 个。猎聘占这个库语料的 84%。
>
> **一条写在最前面的规则，能把后面三处写对的话全部作废。**

> ⚠️ **「CLI 撞限流就改用浏览器」是错的，别再写回来。** 2026-08-19 实测：
> CLI 报 `RATE_LIMITED` 之后打开猎聘浏览器搜索页，安全中心当场要短信验证、
> 账号被标「行为异常」。换通道只是把软限流升级成硬风控。撞限流的正确动作是
> `python tools/portal_budget.py --block liepin-search`，猎聘的 **CLI 那条**停
> 24 小时（见 `job-auto.md` 停手条件）。
>
> **停的是 CLI 那一条，不是整家。** 浏览器那条不停、但会自动放慢
> （间隔 ×3）—— 2026-08-21 用户裁定，
> 理由见下面那张不对称表。所以「CLI 撞了就整家歇一天」不要再写回来。
>
> 有实际后果：解封要写 `--clear liepin-search`，写成 `liepin-browser` 解不开。

#### 但反过来不成立：浏览器被封，CLI 照常抓

当时给的理由是「限的是账号，两条通道用的是同一个账号」。**2026-08-21 核实后
推翻了**：`liepin-search` 的两处请求头里**没有 `Cookie`、没有 `Authorization`**
（`.agents/skills/liepin-search/cli/src/helpers.ts` 两处 fetch 都可查），
它是全匿名的、压根没有账号。真正共用的是 **IP**。

按错理由封出来的范围也就错了——用户在浏览器里被要求过一次短信验证，
不该让一个与那个账号毫无关系的匿名接口跟着停 24 小时。现在两条**分开判**，
而且是**不对称**的：

| 谁撞上 | 另一条 | 为什么 |
|---|---|---|
| **CLI 撞限流** | 浏览器**放慢，不停** | 同一家、同一个网络出口；按原速换通道就是上面那次教训 |
| **浏览器撞风控** | CLI **照常抓** | 匿名接口与那个账号无关 |

> **「放慢」是 2026-08-21 用户裁定的，原来是硬停。** 他的话：
> 「浏览器其实是刻意访问的，要不 cli 封的时候，浏览器加大访问间隙」。
> 两条通道的访问性质确实不同：浏览器是他已登录的 Chrome、一次一个页面、
> 人在场；CLI 是自动批量。为后者的限流把前者整整停一天，代价是整条渠道。
>
> 闸门自动执行，你不用记：CLI 在冷却里时，`--check <浏览器渠道>` 仍然放行，
> 但**间隔 ×3**，并在放行语里说明。
> **别自己按原速抓** —— 08-19 那次升级是真的。

**解封也分开，因为解法根本不同：**

- **浏览器那条只有用户本人解得了**——短信 / 滑块 / 联系客服，工具永远不代过、
  也永远不按时间自动解。他办完了说一声，跑
  `python tools/portal_budget.py --clear liepin-browser`。
- ⚠️ **CLI 那条的限流是 IP 级的，等不掉。**（2026-08-26 本人：「猎聘 cli 封 ip 了，
  需要手动更换 ip 而不是等冷却。在停止时间使用猎聘浏览器获取」。）

  冷却计时照常走——它挡的是「别再往同一个出口上撞」。但**剩余时间不是解法**：
  到点换的还是同一个 IP，探一次限一次，然后再封一天。实测 08-24、08-25 各撞一次，
  第二次就是冷却刚过撞的。

  所以 CLI 封着时只有两个动作，跟钟表无关：

  1. **换 IP**（换网络出口 / 重拨 / 换热点），再按下面那条探一次；
  2. **这段时间走猎聘浏览器**——它是**该走的那条**，不是备胎（判据见本节开头
     那张渠道点名表第 2 行）。放慢照旧（间隔 ×3），但放慢不等于不走。
     实测 2026-08-25：CLI 封着时猎聘浏览器搜一页 40 张卡、新增 36 个，
     而同一天另外三家合计才 50 个。

  **别把「等冷却」写进报告当下一步**——那句话会让用户干等一天，而那一天里
  浏览器那条一直是通的。

- **CLI 那条探一次就知道**（前提是**换过 IP 了**）。这是用户 2026-08-21 点名要的：
  「cli 应该有手动重试来检测是否回复正常了」。走 `/job-scrape health liepin-search`
  ——那本来就是一次哨兵探测。**体检模式自带的额度就是它的上限**
  （一次搜索、至多一次网络重试）；上限之外**不要再探第二轮**，
  哪怕很想让它通。
  **通了就 `--clear liepin-search`，没通就照实说还在限流。**

  ⚠️ **探之前那次额度检查要写成 `--check liepin-search --probe`。**
  不加 `--probe` 的普通检查会照常退出码 1 —— 探测要穿过的正是它要测的那道门。
  `--probe` 只免风控冷却（动作间隔照旧要守），且只对 CLI 生效。
  探测由**用户开口**触发，不进常规轮次、也不自动重试；这与「AI 不代过验证、
  撞限流不自己重试」是同一条边界，变的只是「他问一句时能不能替他探一下」。

⚠️ **间隔不按通道分，按整家算。** 共用 IP 是真的：CLI 发的和浏览器发的
落在同一条时间线上，隔够 8 秒说的是**这家**上一个动作到现在。
**分开的只有封控，不是间隔。**

> 次数上限已经没有了（2026-08-26）：那些数是我们自己拍的，
> 而额度该由平台判 —— 撞到 `--block` 才算。剩下的唯一控制就是间隔。

### Step 0.45：四家**并行**跑，顺位只用来分额度

> **浏览器那几条是等同的，一起跑（2026-08-28 用户裁定）。** 原话：
> 「浏览器渠道是等同的，应该一起去跑。」
>
> 顺位表里那些命中率、容量数是**额度不够时**的分配依据 —— 不是「先跑谁、
> 再看要不要跑下一个」的排队号。四条浏览器通道（猎聘浏览器 / BOSS / 智联 /
> 前程无忧）**同一轮里一起开工**，不因为哪一家「平时产得少」就少给它一次。
>
> 实测代价（2026-08-27 一轮 `/job-auto`，从 `query_log` 数出来的）：
>
>     猎聘 CLI        8 次查询   140 个新岗
>     猎聘 · 浏览器    0 次       0        ← CLI 撞 RATE_LIMITED，没换道
>     BOSS · 浏览器    4 次      28
>     智联 · 浏览器    1 次      15        ← 同是浏览器，只给了 BOSS 的四分之一
>     前程无忧 · 浏览器 0 次       0        ← 闸门放行，没人去
>
> **0 次查询是「没打开过」，不是「跑了没收获」。** 闸门当时四家全放行。
> 而前程无忧是四家里单轮容量最大的一家（50 页，`cdp-portals.md` 的实测表）。
>
> 猎聘那条尤其难看：上面 Step 0.4 那段引用块记着 **2026-08-25 犯过一模一样的错**，
> 规则为此推翻重写过一次 —— 三天后又犯。**规则改对了，执行照旧，
> 因为没有任何东西在验它。** 现在有了：`audit_pipeline` 的
> 「上一轮有渠道整条没跑」按 `query_log` 逐轮数，缺哪条报哪条。


**四家是四个独立账号，没有任何理由串起来跑。** 智联的限流跟猎聘的额度毫无关系，
一家撞了风控也不影响另外三家——所以正确的形状是**同时开工**：

- 猎聘走 CLI，是**另一个进程**，它跑的时候浏览器完全空着；
- 浏览器三家各开各的标签页，用 `browser_batch` 把一次往返里能做的动作打包；
- 谁先跑完谁先进预筛，不等别人。

> ⚠️ **并行只跨平台，不跨同一家的内部。** 同一家的动作要按 `MIN_ACTION_GAP_S`
> 隔开——那正是额度闸门要管的密度。把一家的翻页并发出去，就是在制造
> 2026-08-19 那次 `_security_check`。**跨账号并行安全，同账号并发危险。**

那顺位还有什么用？**额度不够时决定先花在谁身上。** 实测（2026-08-19）：

| 平台 | 抓到 | 可投 | 命中率 | 单轮容量 |
|---|---|---|---|---|
| BOSS | 126 | 17 | **13.5%** | 一次 15 条封顶，没有下一页 |
| 智联 | 70 | 4 | 5.7% | 20 条/页 × 5 页 |
| 猎聘 | 2232 | 107 | 4.8% | CLI 20 条 × 10 页 |
| 前程无忧 | 194 | **0** | 0.0% | 50 页最深，但读不到 JD |

**命中率最高的那家抓得最少**（BOSS 只占全库 4.8%，却贡献了七分之一的可投岗）。
所以时间花下去时，优先级是 **BOSS > 智联 > 猎聘 > 前程无忧**——
它决定的是「这一轮谁多翻一页」，不是「谁先开始」。次数没有上限了
（2026-08-26），但每个动作都要挂 8 秒，**顺序仍然值钱**。

前程无忧排最后是因为它的列表页拿不到逐岗链接，194 个岗至今 0 个可投——
**在它的 JD 取数打通之前，它只值得花一次动作看看有没有新岗**，不要翻页。

### Step 0.46：额度闸门 —— 开关说「要不要」，额度说「现在能不能」

**开关开着不等于现在能抓。** 每家动手前先问一次：

```bash
python tools/portal_budget.py            # 一眼看四家的状态
python tools/portal_budget.py --check liepin-search # 见下：先分清它在说哪一种停
python tools/portal_budget.py --wait navigate --portal 猎聘 # 睡够间隔再动手
```

#### 工具说「停手」时，**先分清是哪一种停**

**退出码 1 不等于这条渠道今天没戏。** 三种停长得一模一样，处理方式完全相反：

| 它说什么 | 是哪一种 | 你该做什么 |
|---|---|---|
| 「动作太密：上一个是 navigate，要隔 8 秒，现在才 0.4 秒」 | **等**，不是停 | 跑 `--wait navigate --portal <平台>`，睡够了接着抓。**一步都不用少** |
| 「猎聘 的 CLI 停着（…）」而你要走的是浏览器 | **名字给错了** | 你问的是 CLI 那条。用你**接下来真要走的那条渠道名**再问一次（`liepin-browser`） |
| 「XX 的浏览器停着（要短信验证）……不会自动解」 | **真封着** | 只跳过**这一条通道**，别跳整家；在覆盖报告里单列一行 |

怎么分：

1. 话里有**「太密」** → 第一种，**等**。跑 `--wait` 就过去了。
2. 话里有**「停着」** → 那条通道确实封着。**接着看它点的是不是你要走的那条**：
   不是（比如你要开浏览器，它说的是 CLI）→ 第二种，换渠道名重问一次；
   是 → 第三种，只跳这一条通道。

第 2 步那个「接着看」不能省。`--check <平台名>` 会落到**此刻真走得通的那条**，
而 `--check <渠道名>` 只答那一条 —— 拿后者的答案去判整家，就是把一条通着的
渠道判死。

> **这一节是 2026-08-26 一天之内栽三次栽出来的**，三次都是同一个形状：
> 工具报了一个不存在的「停」，而流程教的是见 1 就收尾，于是**整条通着的渠道** 
> 闲置一整天。
>
> 1. **记账把自己劝退了。** 记账那条（`--note`）在记完之后才问闸门，于是拿刚写下的那条
>    动作跟自己比间隔，gap 恒等于 0.x 秒 —— 四家平台全中，**每记一次账就回
>    一次「记下了，但到线了」并返回退出码 1**。
> 2. **额度是我们自己拍的。** 每轮 10 次动作、每天 2 轮、每天 60 次请求，
>    没有一个来自平台。当天猎聘和 BOSS 都是被「今天已经跑满 2 轮」停掉的，
>    而两条通道都是好的。四个数当天全删了（本人裁定：额度该由平台判，
>    撞到才算，我们只控间隔）。
> 3. **名字给错了当成整家没戏。** 执行者敲了 `--round liepin` —— 而 `liepin`
>    在这套命名里指的是 CLI 那条通道（`CLI_CHANNELS`），不是整家。CLI 正封着，
>    于是它照实拒绝，而执行者差点据此判定猎聘整家不能动。
>
> 第 3 条最值得记：文档里**早就写着**「渠道名要给准」，照样栽了。
> 一条只在出错之后才想得起来的规则，等于没有规则 —— 所以它现在是上面那张
> 表的第二行，和另外两种停摆在一起，**在读到退出码的那一刻就该被读到**。

- 返回「停手」的**那条通道**这一轮跳过，在覆盖报告里单列一行、写清原因与剩余冷却时间
  ——和「你把它关了」一样要单列，别混进「抓失败」。
  ⚠️ **跳的是通道，不是整家**（同本文件 Step 0.44）。上面那条 `--check` 给的是
  渠道名，它退 1 只说明**那一条**不能走。猎聘还有浏览器那条，CLI 冷却时它
  按**放慢后的间隔**照跑（间隔 ×3，取值只有一处：`portal_budget.SLOW_GAP_FACTOR`）
  —— 用 `--check 猎聘` 问一次就知道（裸平台名会落到此刻
  真走得通的那条）。这里原来写的是「整家跳过」，和 Step 0.44「停的是 CLI
  那一条，不是整家」当面打架，而执行者读到的是这一行：
  **那套不对称闸门在唯一消费它的路径上被读成了空转。**

  > ⚠️ **这两处原来写的是「按 1/7 速率照跑」，而同一份文件另外六处写的是
  > 「间隔 ×3」，代码里也是 `SLOW_GAP_FACTOR = 3`（注释还特地写着「现在**只剩**
  > 间隔 ×3」）。同一个降速档，一份文档里两个数，且少数派那个哪边都对不上 ——
  > 7 这个数在 `portal_budget.py` 里查无出处。**
  >
  > 代价落在最贵的那一格：这是「刚被限流的那家还能跑多快」。读到 1/7 的人
  > 会把猎聘浏览器压到实际的 43%，而猎聘占这个库语料的 84%；反过来，
  > 若有人认定 1/7 才对，就会把另外六处写对的话当成错的去「订正」。
  > 数只留一处：`SLOW_GAP_FACTOR`。2026-09-02 通读时发现。
- 抓的过程中每做一次页面动作记一笔，**带上动作类型**：
  `--note <平台> --kind navigate|fetch|click|read`。类型决定下一次要隔多久
  （整页加载 8 秒 / 同源 fetch 4 秒 / 点卡片 3 秒 / 纯读 DOM 0 秒）。
- **过间隔用 `--wait <类型> --portal <平台>`，它会真的睡够**；`--check` 只会
  告诉你太密、不会拦住你——2026-08-20 实测三次点卡片用了 1.8-2.2 秒就是这么过去的。
- ⚠️ **`browser_batch` 里不许放两个发请求的动作**（两个 navigate、navigate + click…）。
  它把动作打包成一次往返、**中间零延迟**，在平台看来是 0 毫秒内连开两个页面。
  详见 `cdp-portals.md`「间隔按动作的轻重分级」那张表（取值只有一处：`portal_budget.GAP_S`）。
- 撞了验证码 / 风控页 → `--block <撞上的那条渠道> --why "…"`，**那条通道**
  24 小时冷却（渠道名要给准：`liepin-search` / `liepin-browser`）。
  **CLI 撞限流之后不要按原速换浏览器**——浏览器那条**放慢、不停**（间隔 ×3），
  闸门自己会降，你照着 `--check` 走就行（判据见 `job-auto.md` 停手条件那两条实测）；
  反过来浏览器被封时 CLI 照常，见 Step 0.44 那张不对称表。

> **为什么闸门要单独立一步，而不是塞进上面那个开关。** 两件事的主人不同：
> `portals.json` 是**用户**说这一轮想不想抓这家；额度是**平台**说现在还让不让抓。
> 合并之后必然出现「用户明明开着，工具却不抓」而没人解释得清是哪一层挡的。

### Step 0.5：抓就抓，只把比例失衡报出来

> **这一节原来是一道判据，2026-08-27 用户裁定去掉。** 原话：
> 「job-scrape.md Step 0.5 的判据是假的，去除。**你不该因为任何原因限制浏览器的使用**。」
>
> 原来那张表按「可投的岗够不够 5 个」「待评队列空不空」分三种情况，其中一种是
> **先别抓**（队列还堆着时，说「缺的不是岗，是评」）。它的立论是 2026-08-12 那次
> 实测：一轮抓回 210 个新岗、同日只评掉 12 个，待评堆到 589。
>
> **那个立论已经不成立了。** 它成立的前提是「评比抓慢得多」，而那个前提来自
> 「抓完停在待评」的旧流程。现在抓完自动评（Step 5.5）、`/job-auto` 把抓-评-出材料
> 接成了循环 —— 积压不是被这道判据拦住的，是被接缝焊死之后自然消失的。
> 实测同一天（2026-08-27）：一轮抓回 140 个，当天全部评完、出了 7 份材料。
>
> **而它造成的实际损害是可见的。** 同一天执行者照这张表判定「队列还有一堆 →
> 先别抓」，于是 BOSS、智联、前程三家整轮一个新岗都没抓 ——
> **而那三家只有浏览器这一条路**。一道为「防积压」写的判据，实际效果是关掉了三家渠道。

抓多少不设门槛，词表跑到哪算哪（挖空的词由 `query_yield` 剪，见 Step 4.6）。
**唯一保留的是报数**，因为它不拦人：

**每组查询跑完就看一眼待评队列**；队列比「可投的岗 × 10」还长时，在报告里如实说
一句「这轮又加了 N 个待评，队列已经 M 个，评的速度跟不上抓的速度」。
说出来比拦住更重要——用户看得见比例失衡，自己会决定下一轮先干哪件。

### Step 1：搜

搜索策略读 `profile/search-queries.md`（那里是这个用户自己的查询词；
文件不在就让他先跑 `/job-setup`）。

**默认跑全部优先级分类，再按实测产出剪枝**——不是跑前几类。剪掉两种：

1. `QUERY-YIELD` 里在**这个平台上已经挖空**的词（上一轮新增为 0）；
2. `search-queries.md`「实测低效、可跳过的关键词」那一节点名的词。

剪完剩下的全跑，并优先补「达标的词 × 还没跑过的平台」那些格子。

> **原来的默认是「只跑前 3 个优先级分类」，2026-08-12 改掉。**
>
> - 它**按顺序**截断，而顺序是当初拍的；真正该截的是「跑了没用的」，
>   而这件事工具**早就实测出来了**（`QUERY-YIELD` 表 + 「实测低效」清单）。
>   拿一个猜的顺序去替代一份实测数据，是这条命令最贵的一处将就。
> - 「优先级 4：兜底」于是**从来没有自动跑过**。实测后果：某用户
>   1127 个岗全部评完，「值得投」那一档 50 个投光、补不上货——
>   而兜底那一类一次都没跑。
> - 「实测低效、可跳过的关键词」那一节更离谱：**写在资料里，正文从没读过它**。
>   用户（或 `/job-setup`）辛苦记下来的负面结论，一直没有任何代码路径用到。
>
> 剪枝比截断严格更优：它按证据剪、按平台分别剪，而且随每轮实测自动更新。

用户说了 `broad` → **连剪掉的也重跑一遍**（挖空的词过一阵可能又有新岗，
低效词也可能因为市场变化翻身）。这是 `broad` 现在唯一的含义——
「跑全部分类」已经是默认了。

用户给了方向词 → 优先跑那一类的查询（方向词按活动用户资料里的目标岗位理解，
不要预设行业）。

**先读 `QUERY-YIELD` 那一块，再决定跑哪些词。** 该块由 `tools/query_yield.py`
按上一轮实测写入（见 Step 4.6），给的是「每个词在每个平台带来过多少新岗、其中多少
匹配度高」。用它做两件事：

1. **同一平台上已挖空的词不要重复跑。** 实测某 6 个词在猎聘第一轮出 75 个、
   **同一天第二轮出 0**。照着旧列表原样再跑一遍是纯浪费。
2. **优先补「达标的词 × 还没跑过的平台」那些格子**（表里显示为 `—`）——工具会直接
   把清单打出来。同一批词换个平台仍是全新的，实测一轮出 67 个。

**该块之外还要自己想新角度。** 词表只会记录跑过的词，不会凭空长出新的；
本轮 4 个从没试过的角度就贡献了猎聘 87 个新增里的 61 个。跑完新角度，
Step 4.6 会把它们连同实测产出一起记下来，下一轮就不必再想一遍。

⚠️ **候选人资料变了，词表要跟着变。** 实测踩过：`profile/candidate.md` 新增了
「AI 提效 → 真实强项」这条判据，而 `search-queries.md` 的校准注释还停在两周前，
于是**新认定的强项一次都没被搜过**。开跑前对一眼两份文件的日期。

**分级编排。** 不同的招聘网站用不同的覆盖方式——**一家一议，不要把一种机制硬套到所有家**：

- **猎聘 → 走 CLI。** 它有一个能用的免登录 JSON 接口；跑它的 `liepin-search` CLI（1b 会自动发现）。这一条不变。
- **BOSS 直聘 / 智联招聘 / 前程无忧 → 走浏览器，都不行才 `site:` 兜底。** 这三家**没有能用的免登录接口**（BOSS 撞风控、智联返回空诱饵、51job 接口撞 WAF；实测见 `workflows/reference/cdp-portals.md`），所以本项目**有意不给它们做 CLI**——做了也只会静默返回 0 条。它们**走浏览器**覆盖（顺位见 1b.5：先用工具自带的浏览器能力，没有才用 CDP skill），都没有才退到 `site:` 网络搜索。**三家都建议有登录态**：BOSS 与智联未登录拿不到职位；前程无忧未登录也能读，但拿到的是本地泛招聘，**登录后裸入口才按账号求职期望个性化**（2026-08-19 实测）。**字段最全的是智联**，不是前程无忧——各家实际给哪些字段见 `cdp-portals.md` 的实测表。另见 `workflows/reference/cdp-portals.md` 与下面的 1b.5 小节。
- **其它没接过的渠道 → `site:` 兜底**，或者建议跑 `/job-add-portal`——但**只给真的暴露了可用免登录接口的网站做 CLI**。**不要做一个只会静默返回 0 条的 CLI。**

**有 CLI 的渠道，就以 CLI 为主力搜索手段。** 没有 CLI 技能、浏览器渠道也覆盖不到的，或者机器上没有 CLI 运行时（node / bun）时，退到网络搜索（1c）。 **这道运行时门只影响 CLI 渠道（猎聘）。** 浏览器渠道（BOSS/智联/前程，见 1b.5）不依赖 node/bun——运行时缺失从不降级浏览器渠道。

#### 1a. 先看 CLI 跑不跑得起来

portal CLI 是零 runtime 依赖的 TypeScript 源码，**没有编译步骤**，node 与 bun 都能直接跑。
**node 是默认路径**：Node 在绝大多数机器上已经有了，但**别从「他装了哪家 AI 工具」反推**
——各家装法不一样（有的走 npm、有的是原生可执行文件），下面那条 `node --version`
就是当场量它用的。用户不必额外装 Bun。

```bash
node --version    # 需要 v22.18+（默认剥离 TS 类型；22.6 起要加开关，不算）
```

- **v22.18 或更高** → 用 `node <cli.ts> …` 调用（下文 1b 的命令一律用这个形式）。
- **低于 v22.18，或 node 不可用** → 试 `bun --version`；可用就把命令换成
  `bun run <cli.ts> …`，行为一致。
- **两个都不可用** → **仅 CLI 渠道**（猎聘）失去主路径，转 **1c（网络搜索兜底）**，
  并在 Step 5 的输出里标注该渠道实际走的是兜底。

这**不影响**浏览器渠道（BOSS/智联/前程）：它们的 1b.5 流程走浏览器，
与 node/bun 无关，照常进行。

#### 1b. 跑 CLI（主力 —— 能并行就并行）

读遍 `.agents/skills/*/SKILL.md`，把已装的渠道 CLI 全找出来。

> ⚠️ **那底下不全是渠道。** 判据是**有没有 `.agents/skills/*/cli/src/cli.ts`** ——有才是渠道技能。
> 同一层还放着命令的技能壳（`job-application-assistant` 那份手写的路由壳，加上
> `tools/gen_entries.py` 按 `workflows/INDEX.md` 生成的那 21 份），那是同一份壳按各家 AI 工具的
> 约定各放一处，**不是渠道**：没有 CLI，也没有 `url-reference.md`。
> 照目录名一把捞，捞出来的绝大多数都不是渠道（2026-08-31 实测：4 个目录、1 个渠道）。

每份 `SKILL.md` 都写着那个渠道**确切的命令行参数与用法示例**。**照它写的接口用，不要猜参数。**这样一来，`/job-add-portal` 新接进来的渠道会自动被认到，不必改本文件。

**开关要认。** 除非某个渠道的 `SKILL.md` frontmatter 写了 `enabled: false`，否则一律算开着（**没写这个键就是开着**，那是默认）。关着的跳过，并记下来给 Step 5 的汇总用。这样一来，装着但这轮不跑是可以的，不必删目录。

对每个**开着的**渠道技能：

1. 读它的 `SKILL.md`，找到正确的调用方式与支持的参数。命令前缀用 1a 定下的那个（`node <cli.ts>` 或 `bun run <cli.ts>`）。
2. 把 `profile/search-queries.md` 里的查询词，翻成这个渠道认的参数形式（`--key`、`--search-string`、`--query`、筛选码……以它自己的 `SKILL.md` 为准）。
3. 用这个渠道支持的「多久之内」参数，把范围收到**最近 14 天**（`--jobage`、`--since <YYYY-MM-DD>`、`--order PublicationDate` 等，各家不同，照它的文档来）。

   > ⚠️ **「多久之内」是在结果上过滤的，没有日期的会被一起丢掉。**
   > 猎聘 CLI 的 `meta` 里分开报了两个数：`droppedTooOld` 和 `droppedNoDate`
   > —— **看第二个**。它偏大意味着这一轮丢掉的多半不是旧岗，是**没标日期的岗**，
   > 那些可能全是新的。这时候**这个词这一轮别传 `--jobage` 再跑一次**。
   >
   > ⚠️ **这条原来说「翻页的时候干脆别传它」，2026-08-27 那个前提被实测推翻了。**
   >
   > 原来的依据（2026-08-23 全库分组）：带日期的比例 **第 1 页 250/860（29%）·
   > 第 2 页往后 9/710（1%）**，据此得出「`--jobage` 在第 2 页之后几乎会把结果清空」。
   >
   > 而 2026-08-27 一轮 `/job-auto` 从同一个 CLI、同样不传 `--jobage` 抓了 8 次
   > （4 个词 × 前 2 页），入库 140 个：**第 1 页 97/97、第 2 页 43/43，
   > 两边都是 100% 带日期。** 同样的调用方式，深页的日期覆盖率从 1% 变成 100%。
   >
   > **所以「深页没日期」不是页码的性质，是当时那批数据的性质**（接口行为变过，
   > 或者早期入库那批的页码标注口径与现在不同）。全库现在是第 1 页 17%、
   > 深页 7% —— 差距还在，但只有 2 倍多，撑不起「几乎清空」那个结论。
   >
   > **改成：翻页时照常可以传 `--jobage`，但每一轮都看一眼 `droppedNoDate`**
   > （上一段那条事后补救仍然有效，而且它本来就是更可靠的判据 ——
   > 它看的是这一次请求的实际情况，不是一个会过期的分布）。
   >
   > 不看它的代价在下一步：`query_yield` 按产出剪掉「挖空的词」——
   > 一个词的结果全因缺日期被丢光，它会被当成挖空剪掉，而那是误判。
   > 别的渠道没有这两个数时，如实说「这一轮丢了多少不知道」，不要当成 0。
4. 用它的条数参数，每次调用**收到 20 条左右**。
5. 加 `--format json`，要机器能读的输出。

   > ⚠️ **除了「城市」和「多久之内」，其余原生筛选参数一律不传。**
   >
   > 猎聘 CLI 还给了 `--edu` / `--years` / `--salary` / `--industry` /
   > `--comp-scale`（别家类似）。它们看起来是白捡的效率 —— 少抓一批不合适的，
   > 省额度、省评分。**别捡。** 三条理由，前两条是量出来的：
   >
   > **一、服务端过滤没有泊车、也没有回收。** 客户端把一个岗降权泊在库里，
   > 你还能回头翻；服务端排掉的那批**从来没进过库**，你不知道它们存在过。
   > 实测活动用户 2026-08-24（库里 2638 个岗）：
   >
   > | 传了这个 | 会被排掉 | 其中本来评到「可以投」三档的 |
   > |---|---|---|
   > | `--edu`（按本科） | 283 个要求硕士/博士的 | **24 个（8%）** |
   > | `--industry`（锁行业） | 225 个行业字段为空的 | **57 个**；而可投三档横跨 **68 个行业** |
   > | `--comp-scale` | 319 个规模字段为空的 | **68 个** |
   > | `--salary` | 31 个薪资写「面议」或空的 | 5 个 |
   >
   > 每一行的第三列都是**静默损失** —— 不是「少看几个烂岗」，是「有几个能投的
   > 你永远不会知道」。空值那几行尤其要命：字段没填不等于不合适，而服务端
   > 一律当不合适。
   >
   > **二、列表页那几个字段是展示值，不是 JD 的真实要求。** `prescreen.py`
   > 自己量过：`eduLevel` 与 JD 正文 **58% 对不上**，所以它只肯降权泊车、
   > 不肯据此判死。同一个字段拿到服务端去用，等于把一个 58% 不准的判据
   > 升级成一票否决，还看不见。
   >
   > **三、传错值会伪装成限流。** 这几个参数收的是猎聘的筛选码；值不合法时
   > 接口返回 `flag !== 1`，和限流长得一模一样（`.agents/skills/liepin-search/SKILL.md`
   > 「注意事项」写着这条）。而本仓库撞见限流就记额度封控 —— 一个拼错的
   > 筛选码能把整家停 24 小时。
   >
   > **`--location` 是例外**（猎聘 CLI 里它必填），`--jobage` 是例外
   > （上一条刚讲完怎么用）。这两个的共同点：它们过滤的是**客观事实**
   > （城市、发布时间），不是「这个岗要不要得起你」那种判断。
   > 判断留在客户端 —— 那里有泊车、有回收、有 JD 正文。

能并行就并行——用并行子代理那项能力（没有这项能力就改成一个个串着跑，见 `AGENTS.md` 的能力对照表）。把各家的 `results` 汇成**一个池子**交给 Step 2，**每条都要带着它是从哪个渠道来的**（Step 2 取详情时要按渠道调 `detail`）。

某个 CLI 非零退出时，**把错误记下来然后继续**——不要因为一家挂了就中止整轮搜索。

#### 1b.5. 浏览器渠道 (BOSS 直聘 / 智联招聘 / 前程无忧)

这三家没有 CLI（顺位见上面那段）。它们**走浏览器**覆盖，
而浏览器怎么选有先后 —— **不要搞反**：

| 顺位 | 用什么 | 为什么在这个位置 |
|---|---|---|
| 1 | **你所在 AI 工具自带的浏览器能力**（见 AGENTS.md 能力对照表「浏览器取数与页面操作」一行） | 驱动的就是用户自己那个已登录的 Chrome，登录态天然带着；用户不必装任何第三方东西。**需要在页面上点/填/滚动（GUI 操作）时尤其用它。** |
| 2 | **web-access skill 的 CDP 代理** | 只在没有扩展、或扩展够不着时才用。它是第三方全局技能，**本项目不附带**，要用户自己装一次。 |
| 3 | **`site:` 域名限定网络搜索**（1c） | 前两者都没有时的兜底，字段少得多，必须在覆盖报告里如实说明。 |

逐层这么走：

0. **先查登录态，缺哪家立刻告诉用户**（`cdp-portals.md`「开跑前先查登录态」）。
   未登录的渠道**停下来问**，别静默跳过——用户登录只要几秒，跳过等于这一轮
   整家不要了。尤其前程无忧：未登录也返回结果，只是**结果与他的求职期望无关**，
   不查就抓会拿回一堆没有任何报错的错岗。

1. **先看第 1 顺位能不能用**：你这个工具本身能开浏览器吗（对照 AGENTS.md 能力表
   查你这个工具落在哪）？能就直接用它，**不要**再去加载 `web-access`。
   够不着时才降到第 2 顺位，加载 `web-access` 并让它的 `check-deps` 判定。
   登录态只对 **BOSS 与智联**是硬要求（未登录拿不到职位）；**前程无忧未登录也能读**，
   所以即使用户没登 51job 也照跑。
2. **有浏览器渠道（顺位 1 或 2）→ 跑浏览器流程。** 按 `workflows/reference/cdp-portals.md`
   的步骤做（开一个后台标签页、滚动加载、把职位卡读成结构化字段、对 `seen_jobs.json`
   去重）——那份文档记的是**页面结构与站点实测经验**，两个顺位都适用，只是驱动浏览器的
   手段不同。**它的账号安全铁律要照办**——低频、不批量、
   **一撞验证码或风控就停手**。抽到的岗并进 Step 2-4 同一个池子，并标上是哪个渠道。
   - **先用账号的求职期望，别急着拼查询。** BOSS 与智联登录后，**裸搜索页本身就已按用户站内设置的「求职期望」过滤好岗位与城市**（智联连区都带）。先开裸入口读出当前期望，覆盖得住就直接取；只有要搜期望之外的岗位/城市时才收窄，且优先用页面 UI 而非拼 URL。详见 cdp-portals.md「通用流程」第 3 步。
   - **BOSS 的薪资是字体混淆的**（PUA 码点 + 自定义字体），`innerText` 只会读到 `-K`。按 cdp-portals.md「BOSS 薪资」一节每轮自解，**不要硬编码映射**；解不出就标「未知」。
   - **浏览器跑了、但结果很少或没有**（一个冷门查询只出 0-2 张卡）：**不要**把这么稀薄的结果当成完整覆盖。**再对这个渠道跑一次 `site:` 网络搜索（1c）补上**，并在 Step 5 的覆盖报告里如实说明：这个渠道用浏览器只搜到很少，已用 `site:` 搜索补过。**`site:` 兜底不只在浏览器不可用时触发，结果稀薄时同样要触发。**
3. **两个顺位都不可用**（没有浏览器扩展、`web-access` 也没装或检查不过、或撞了风控已停手）
   **→ 退到 `site:` 网络搜索（1c）** 覆盖该渠道。

**别为此放宽权限。** 走第 2 顺位时，CDP 委托给 `web-access` skill，由它自管本地
CDP-Proxy 的 curl 与风险提示；**不要**往这条工作流的触发壳或项目权限设置里加 `Bash(curl:*)`
之类——以 skill 方式调用它。走第 1 顺位则用工具自带的浏览器工具，同样不需要额外权限。

**逐个渠道记下走的是哪一顺位**（工具自带浏览器 / CDP skill / 仅 `site:` 兜底），
以及是否被 `site:` 补充过，好让 Step 5 的覆盖报告用大白话如实说明。

#### 1c. 网络搜索兜底

这几种情况用网络搜索能力：
- `profile/search-queries.md` 里点了名（或者按框架 `search-queries.md` 那套 `site:` 兜底结构）、但 `.agents/skills/` 下**没有对应目录**的渠道
- 任何一家 CLI 跑挂了的渠道
- 一个 CLI 运行时都没有的时候（Step 1a 没过）

每条网络搜索的拼法：**框架 `search-queries.md` 里那套 `site:` 域名模板**（结构）＋ **`profile/search-queries.md` 里用户真实的关键词**（内容）。

### Step 2：取详情、解析

Step 1 里每一条看着有戏的结果：

**CLI 来的：** 搜索结果里已经有职位名、公司、地点、日期和链接了。
值得细看的那些，再用那个渠道的 `detail` 命令取完整详情
（照它的 `SKILL.md` 来，**不要猜参数**），从中取出**关键任职要求**、
**投递截止日期**，以及一小段描述。

**网络搜索来的：** 对职位链接用网页抓取能力（没有这项能力时怎么办，
见 `AGENTS.md` 的能力对照表），把同样那几个字段手工抽出来。

**浏览器来的（BOSS / 智联 / 前程无忧，以及猎聘 CLI 停着时的猎聘）：**
详情页打开的那一刻，JD 正文就在眼前 —— **当场存下来，一个岗一次**：

```bash
python tools/jd_store.py --save <职位链接> --apply <<'JD'
<把整段 JD 正文粘在这里>
JD
```

> ⚠️ **这一条原来只写在 Step 4.5，而 Step 4.5 是照 CLI 那条路写的**
> （`--import-from <抓好的目录>`、「详情接口返回的是搜索结果的超集」）。
> 浏览器这条根本没有「抓好的目录」：正文是在 Step 2 打开页面时看到的，
> 走到 4.5 页面早关了。**规则没缺，缺的是它没长在正文在眼前的那一步。**
>
> 实测代价（2026-08-30 按渠道量的 JD 覆盖率）：
>
> | 渠道 | 岗数 | 有 JD | 覆盖率 |
> |---|---|---|---|
> | `liepin-browser` | 48 | 47 | **98%** |
> | `boss-browser` | 81 | 49 | 60% |
> | `51job-browser` | 53 | 16 | 30% |
> | `zhaopin-browser` | 65 | 14 | **22%** |
>
> `liepin-browser` 98% 说明**浏览器这条完全存得下**，不是能力问题；
> 差别在于猎聘那条是 CLI 停摆时临时走的、执行者顺手就存了，
> 而另外三家是常态渠道，反倒一直在丢。
>
> 丢掉的后果不是「回头补一次」那么轻：算能力差距（`/job-upskill`）少这一份语料、
> 复查原文时无从核对、**岗位下线之后就永远查不回来了**；而回头补要重开页面、
> 再花一次额度，还要重排列表（`fetch_details --browser-list` 那条路自己也写着
> 「浏览器渠道的 JD 只能在抓取当次取」）。
>
> 落库的判据与另外两种写法（一整个目录的 / 抓取器内部直接调）见 Step 4.5。

每一条候选都要过这两道：
- 「链接 + 职位名」已经在库里（**热库 ∪ 存档**，用 `_cli.seen_index`，见 Step 4）→ 跳过
- 「公司 + 职位名」这一对已经在 `seen_jobs.json` 里（同岗换了链接的兜底）→ 跳过
- 「公司 + 岗位」已经出现在 `job_search_tracker.csv` 里（投过了）→ 跳过

### Step 2.5：同一份 JD 被广撒（只看这一轮之内）

这是一个**值得提醒用户留意的分发特征，不是对雇主的指控**——它描述的是这条招聘**在怎么被撒出去**，不是在判定这家公司正不正经。它本身证明不了任何问题（同一个岗在好几个城市同时招，完全可能是真的）。**摆出来让用户自己判断值不值得花时间，不要因此扣分，更不要静默把它筛掉。**

这一轮池子里有两条以上（同一家公司，或者链接/标题里能看到同一个需求编号）描述基本相同、只差城市或职位名的，**不要各占一行**。合成一行，把撒的范围写出来，例：「同一个岗在 6 个城市重复挂着（北京、上海、深圳、杭州、成都、武汉）」。

### Step 3：快速匹配判断

每个新岗做一次**快速**匹配判断（**不是** `04-job-evaluation.md` 那套完整评估，只要一个粗信号）：

- **高匹配**：这个岗直接用得上他的核心技能
- **中匹配**：跟他的经历相邻，够得着
- **低匹配**：要的技能他缺得比较多

### Step 4：去重、入库

**键由「链接 + 职位名」派生，所有渠道一律如此**（`_cli.stable_id(url, title)`，
与面板上那个 `id` 同一个函数）；没有 URL 的用 `<渠道>_<公司>_<职位名>` 兜底。
**查重不比键，比「链接 + 职位名」这个身份**——键只是记路用的。

这一句 2026-10-12 之前写的是「键的形态是 `<url>#<职位名>`，**查重时必须把裸 URL
也查一遍**」：那条补丁之所以存在，是因为库里存着历史遗留的裸 URL 键，
只查一种形态就会把同一个岗再插一遍。现在旧键由 `tools/rekey.py` 收成一代，
补丁随之作废——**别再拿键当判据**（下面那条引用记了它漏掉的量）。

⚠️ **链接要先归一化。** 同一个岗在库里可能两种写法都有：页面锚点给什么就存了什么，

#### 查重命中时，只更新一个字段：`date`（岗位刷新时间）

见过的岗**不重新评估、不改判词、不动别的任何字段**——查重的全部意义就在这儿。
但 `date` 是例外，它要跟着这一轮的搜索结果更新（猎聘的 `refreshTime`，别的平台没有就跳过）。

**为什么单单它要更新：**

- 它记的是**招聘方最后一次动这个岗**，是个会变的量；其余字段（标题、公司、
  首见日）都不会变。冻住它等于把一个动态量当静态量存。
- 面板据它标「抓到时已 N 天没刷新」（`export_web_data.posting_age`）。
  不更新的话，一个上周刚被重新刷新的活岗，会因为我们三周前记下的旧时间
  被标成凉了 —— **对健康的岗误报，比不标更坏。**
- 框架第三步的「蓄水池嫌疑」（`04-job-evaluation.md`）**整条建立在这一步上**。
  判据是什么以那份文件为准，**这里不复述** —— 它要的就是「首见很早、刷新很新」
  这个组合，而只有这一步真的更新 `date`，那个组合才可能出现。

  **它已经出现了。** 实测活动用户 2026-08-26：76 个同时有 `date` 与 `first_seen`
  的岗里，**2 个 `date` 晚于 `first_seen`**（都晚 2 天）、14 个同一天、
  60 个仍是首见之后没被顶过。数不大，但它证明这一步在跑 ——
  **这一行原来写着「这条现在算不出来」，而那句话在规则生效之后又留了下来**，
  04 那边解封了、这边还封着，同一件事两个文件说反话。
  下次改这一步之前，先跑 `python tools/audit_pipeline.py` 看「蓄水池那条算不算
  得出来」那一项 —— 它每次都现算，不靠这里这个数。

更新它**不花额外额度**：这一轮的搜索结果里本来就带着这个字段，不必回头再请求。

> **这一行原来写的是 `<url_or_company_title_key>`**，一个含糊的占位词，而

写成 `账号求职期望(<期望名>)`——它也是真实来源，只是不能当查询词跑。

这一条**不是为了好看**。实测代价：库里 991 个岗、没有一个记着来源，于是「哪些词
管用」从来测不出来，每轮只能靠回忆重建。而回忆是错的——补上这个字段当轮就发现：

| 词 | 新增 | 其中高匹配 |
|---|---|---|
| `智能体开发` | 12 | **12（100%）** |
| `Agent产品经理` | 14 | 12（86%） |
| `数字员工` | **39** | **2（5%）** |
| `流程自动化` | 18 | **0** |

上一轮的报告按「新增数」把 `数字员工` 和 `流程自动化` 夸成高产词，**因为当时只有
数量这一个指标**。它们实际带回来的是一堆数字IC设计工程师。**数量不是产出。**

### ⚠️ `query_log`：跑过就要留痕，哪怕一条都没搜到

除了给每个岗写 `found_by`，**每跑一组查询还要往 `seen_jobs.json` 的 `query_log`
记一笔**，形如 `{"query": "AI应用落地", "portal": "liepin-search", "date": "…",
"rows": 0, "new": 0}`。零产出的那些**尤其**要记。

原因是实测撞出来的：`AI应用落地` 在 BOSS/智联各出 15/14 个、高匹配 12 个，
所以工具把「猎聘还没跑过它」列成了下一轮最值钱的格子。跑了——**猎聘返回 0 条**。
而 0 条就没有条目、没有 `found_by`，那一格仍然显示 `—`（没跑过），
**下一轮工具还会再推荐它一次，永远推荐下去**。翻页只拿回重复项也是同一回事
（实测 `智能体开发 p2`、`Agent产品经理 p3` 各跑 17/20 条、新增全为 0）。

有了 `query_log`，表里 `0`（跑了没产出）与 `—`（没跑过）才分得开。
**这个区分就是这张表存在的理由**——分不开的话它给的建议是错的。

`portal` 记的是这条岗**由哪个渠道 CLI 产出**（Step 1b 已经给每条结果打好了标，这里把它落盘）。这个字段出现之前写的老条目没有它；体检（Step 4.75）会拿链接的域名去对各渠道的基址来归属，**所以不要回填**。

`/job-rank` 在这套 schema 上**只增不改**：打过分的条目再带上 `rank_score`（0–100 总分）、`rank_verdict`（判词，如「粗筛：强匹配」）、`rank_date`（评估日期），以及 **`rank_breakdown`**（拆解与依据——面板的技能分、`gap_split` 的四格、`/job-upskill` 的整个第 2 层数据源都读它，落盘形状见 `job-rank.md` Step 4）。`status` 改成 `"ranked"`。
重写条目时这几个字段一个都不能丢。

⚠️ **`evaluated` 是布尔字段，不是 `status` 的取值。** `/job-apply` 深评之后写 `"evaluated": true`，`status` 仍是 `"ranked"`。这份 schema 原来把 `evaluated` 列进了 `status` 枚举里——真写成 `"status": "evaluated"`，那个岗就从每个视图里消失了：`/job-rank` 只挑 `new`、面板按 `ranked` 统计、`gap_split` 也只看 `ranked`，而且**全程不报错**。

2. **只摆出**不在已见列表、也不在投递记录里的岗。

### Step 4.5：顺手把详情抓了，存进详情库

**一趟能拿全的东西不要拆成两趟。** 详情接口返回的是搜索结果的**超集**——
`salary`/`salaryMonths`/`eduLevel`/`compScale`/… 全都有，外加 `description`（JD 正文），
而 JD 正文正是 `/job-rank` 打分要用的那份。列表页永远给不全（实测猎聘详情能补上
`isHeadhunter`/`salaryMonths` 等一批列表页没有的字段）。

对**本轮新增**的职位，逐个取详情，写进 `job_scraper/details/<id>.json`：

```bash
python tools/jd_store.py --import-from <抓好的目录> --merge --apply
```

抓取器批量落了 JSON 的走上面那条；**你自己在浏览器里一个一个读的走**
`python tools/jd_store.py --save <职位链接> --apply`（正文从标准输入进）——
手上只有一段正文时，为了存它先造一个 JSON 文件正是那条规则一直没人执行的原因。
抓取器内部也可以直接调 `jd_store.save()`。抓完跑一次 `--merge` 把结构化字段回填进
`seen_jobs.json`（**只补空缺、不覆盖已有值**，不一致的如实报出来）。

- **`id` 用 `stable_id(url, title)`**，与导出给页面的 `id` 同一个函数。不用 URL 当
  文件名：51job 实测同一 URL 下挂着两个不同职位，按 URL 存会互相覆盖。
- **正文留在详情库，不进 `seen_jobs.json`。** 后者每改一次状态都要整体重写，
  塞进去会让它从 170 KB 涨到 1.6 MB，每标一个「不投」都重写一遍。
- **抓不到就跳过，不要编。** 只有猎聘有可用的详情接口；BOSS 的详情页返回加载页、
  前程无忧撞阿里云 WAF（见 `workflows/job-rank.md` Step 2）。这些渠道本步跳过，
  在覆盖报告里如实说明，`/job-rank` 到时候走浏览器渠道补。
- **遵守节流。** `liepin-search` CLI 已内置 1.5 秒最小间隔与指数退避，**不要绕过它
  并发发请求**。按这个节奏，一轮新增 40 个岗约 1 分钟。撞到风控就停手，
  已抓到的照样存下来——存下来的就不用再抓。

> **为什么单独建一个库，而不是每次现抓。** 早先 `/job-rank` 抓完 JD 打完分就丢掉，
> 于是重跑一次、换个会话、或进程中途挂掉，全部要重抓。实测有一批 137 份 JD 抓完
> 躺在系统临时目录里——那是 137 次请求、三分多钟节流等待的成果，Windows 清一次
> 临时目录就没了。**抓过的就不该再抓。**

### Step 4.6：把这一轮的产出写回词表（不是可选项）

> ⚠️ **扫过的格子必须留痕，哪怕一个岗都没留下。**
> `query_yield.py` 是从 `seen_jobs.json` 的 `found_by` 反推产出的——**没入库的岗它看不见**。
> 于是「这个词在这个平台扫过、全是低薪、一个都没要」这件事**没有任何地方记着**，
> 下一轮的空格子清单里它还在，会被当成新大陆重扫一遍。
>
> 实测（2026-08-13 `/job-auto`）：智联扫了 3 个词共 43 个岗、前程无忧扫了 38 个，
> 因为全在薪资底线以下没入库；跑完产出表照旧显示这 6 个格子是空的。
>
> **所以按薪资/方向筛掉的岗也要入库**，直接落 `status: ranked` + `粗筛：不建议`
> 并写明原因。它们**不是积压**——积压是 `status: new` 那种没人看过的；
> 已结案的条目只占一行 JSON，换来的是「这条路走过了」这个事实不会丢。
> （Step 0.5 防的是「抓得比评得快」，不是「把已判的结论扔掉」。）

```bash
python tools/query_yield.py --apply
```

它按「词 × 平台」聚合 `found_by`，把达标的词写进 `profile/search-queries.md`
里一块带标记的自动维护块（`QUERY-YIELD:BEGIN/END` 之间，幂等重写，人工维护的
「优先级」分类不动）。**这一步交给工具而不是写进流程叮嘱，理由和 `writeback.py`
一样：流程指令 AI 会漏，漏了就没人发现。**

它还会列出「达标的词 × 还没跑过的平台」——那是下一轮最值钱的格子。实测同一批词
在猎聘挖空的同一天，在前程无忧上一轮出 67 个新岗：**「这个词没用了」和「这个词在
这个平台没用了」是两回事。**

### Step 4.75：各渠道体检

**靠刮页面的渠道 CLI 会无声地烂掉**：网站一改标记，解析器通常是「退出码 0、零条结果」，或者字段变成 null 和乱码；而 Step 1c 的兜底只在**硬失败**时才触发，于是永远不会启动。这一步就是拿**这一轮手上已经有的证据**把它抓出来。

**白扫一遍（不额外发任何请求）。** 对 Step 1b 里跑过的每个开着的渠道：

- **看它这一轮返回的结果有没有退化。** 这几种是信号：每一条的 `company` 都是 null 或空、职位名是空的、职位名里带着没解码的实体（`&amp;`）或 HTML 片段、链接根本不指向这个网站。**出现任何一种，就说明解析器半瘫了**，而 `/job-scrape` 正在无声地往库里收垃圾。
- **对一下历史产出：** 这一轮所有查询词在它上面都是零结果时，去 `seen_jobs.json` 里看它以前有没有产出过（看 `portal` 字段；更早的条目就按链接域名匹配）。**以前出过岗、现在一个不出的，可疑**——同样的词以前是管用的。

**升级探测（有额度上限，且只对可疑的做）。** 可疑的渠道给**一次**哨兵探测：用它自己 `SKILL.md` 里那条示例查询跑它记录在案的 `search`（那条词在这个技能登记进来时是**验证过能用的**），条数参数压到 3，加 `--format json`。还是零结果，就**再重试一次**、换一个最常见的单词。到这一步仍然没有，才判**坏了**。**撞 429 或者拦截页永远不算「坏了」**——记成**结论不明（被限流）**，退避，**不要重试**。

**判定怎么报。** 健康的渠道**一个字都不说**——不出表、不出行。其余的都在 Step 5 的汇总里出一行体检结论。

**只体检模式（`/job-scrape health`）。** 跳过 Step 1-4，也跳过这一步的白扫（没有新跑过的一轮可扫）；改成**直接探测每个已装的渠道**——默认只探开着的，关着的只有被点名时才探（例：`/job-scrape health liepin-search`）。每家都做上面那次哨兵探测，对它返回的东西套同一套退化判据；而且——**既然用户是明确来做诊断的**——对每个健康渠道的第一条结果再取一次 `detail`（描述必须是解码正常、能读的文字；取不到就降级为退化）。**这个模式下所有状态都要报，包括健康的。** 用量仍有上限：每家一次搜索、至多一次重试、至多一次详情。

### Step 5：把结果摆出来

新岗摆成一张表，**按匹配度排（高的在前）**。Step 1b 跳过了某些渠道（`enabled: false`）时，
用下面那行 `skipped (disabled):` 把它们报出来——**把某家关掉这件事要看得见，不能悄悄发生**；
一个都没跳过就别出这行。

**如实报覆盖（只在真的搜过的那种运行里报，health 模式不报）。** 真搜过一轮时，
在下面的 `coverage:` 行里**用大白话**说清**每一家**这轮到底是怎么覆盖的——
说实际发生的事：走的 CLI / 登录态浏览器（CDP）/ 网络搜索 `site:` 兜底 / 还是跳过了（为什么）。
**只说实际发生的，不谎称覆盖。**
例：「猎聘：CLI，N 条；BOSS：登录浏览器搜到 M 条（其中遇验证码停手）；智联：未登录，退
site: 兜底；前程：跳过（未登录且无兜底）」。

**`/job-scrape health`（只体检）不出 `coverage:` 行。** 体检模式（Step 4.75 只探测）
跳过了 Step 1-4、一个渠道都没搜，所以**没有真实覆盖可报**——
在那里编几行 `coverage:` 就是编造。只输出体检/探测结论；
如果场合上确实期待一句覆盖说明，就写 `health 模式：本轮未搜索，无覆盖可报告`，
**不要**写任何 `coverage:` 行。这样 BOSS / 智联 / 前程的覆盖每一轮都是诚实的。

Step 4.75 判出某家退化、坏了、或结论不明时，**每个可疑渠道加一行 `health:`**
（健康的不出行）；报完之后，**问用户要不要**把那家的 `enabled` 设成 `false`，
让 `/job-scrape` 在它修好之前不再跑它（改走 Step 1c 兜底覆盖）——
**这个开关只有得到用户确认才动，而且除它之外，那个技能里的任何东西都不许改。**

```
## 新找到的职位 - YYYY-MM-DD

新增 X 个岗位（匹配度：高 Y 个、中 Z 个、低 W 个）。

coverage: 猎聘：CLI，8 条；BOSS 直聘：登录浏览器搜到 5 条；智联招聘：登录后用浏览器抓，结果稀薄，退 site: 兜底补充；前程无忧：未登录，退 site: 兜底

跳过（开关关着）：<渠道名>、<渠道名>

体检：<渠道名> —— 退化（12 条结果的公司名全是空）；解析锚点见 .agents/skills/<渠道名>/url-reference.md
体检：<渠道名> —— 坏了（SKILL.md 里那条示例查询和更宽的重试都是 0 条）；解析锚点见 .agents/skills/<渠道名>/url-reference.md

| # | 匹配度 | 职位 | 公司 | 地点 | 截止 | 链接 |
|---|-----|-------|---------|----------|----------|-----|
| 1 | 高 | … | … | … | … | [打开](…) |

Step 2.5 查出广撒的，**把它写进「职位」那一格**（例如「前端开发工程师（同一个岗挂在 6 个城市）」），**不要埋在下面的详情里**——那是用户应该一眼看见的信号。

### 重点看这几个
匹配度高的每个岗写 2-3 条：
- 为什么和你对得上
- 有哪几条要求要先确认
- 有没有可疑的地方（含 Step 2.5 查出的海投/挂人信号）
```

摆完之后问一句：
> 想细看哪个？给我序号就行。

用户报了序号，就跑 **`/job-apply <该职位的 URL 或粘贴 JD>`** —— **那是投递的唯一正路**。`/job-apply` 是加固过的那条流程：它会跑资料前置检查、硬门 + 四维评估、`← 假设值` 的处理、落盘前的占位符与假设值扫描、照片透传，以及起草-审稿两轮。**真要投递时，不要交给 `job-application-assistant` 那套更早的内联流程**；细致投递永远走 `/job-apply`。

### Step 5.5：抓完直接评，不要停在「待评」

**报完覆盖情况就接着跑 `/job-rank --auto`**（照 `job-rank.md` 全流程：预筛淘汰 →
抓 JD → 硬门 + 四维 → 写回）。默认开着，`--no-rank` 才关。

> **为什么是默认，而不是「建议用户去跑」。**
>
> 这里原来写的是「新岗多（8+）时**也建议** `/job-rank`」。可**「待评的岗」不是一个
> 可用的产物**——它没有分、没过硬门、不知道该不该投，在面板上只是一个计数。
> 用户要的从来是「可以投的岗位」，抓取停在待评就是**交付了半成品**，然后让他自己
> 记得再敲一条命令把它做完。
>
> 而这一步**没有任何需要人判断的输入**：抓多少、评几批、先评哪个都有明确判据
> （`job-auto.md`「什么归机器，什么永远归人」那张表把它们全列在「归机器」一侧）。
> 一个纯机械、判据齐全、不做就等于没做完的步骤，不该由人来触发。
>
> 实测代价：2026-08-12 一轮抓回 210 个新岗，评掉 12 个，**待评堆到 589**。
> 每一轮都靠人记得「再跑一次 rank」，漏一次就多积压一批。

报告分两段，别混：

```
本轮新抓的 N 个：可投 X · 分不够 Y · 硬性条件没过 Z
顺带清掉的积压 M 个：可投 A · …
```

**新抓的排在前面**——那是这次运行的直接结果，用户最想看的是「我刚抓的这批里有什么」。

停手条件、批大小、通道选择全部照 `job-rank.md` 的规定，**这里不另立一套**。
撞风控就停，已抓已评的照常留着。

### Step 6：投递记录归 `/job-outcome`，这里一行都不写

用户说他要投某个岗时，**不要自己往 `job_search_tracker.csv` 里加行** ——
告诉他材料备好之后怎么记：

```
/job-outcome <公司>
```

（总览页开着的话，那一行上的「我投了」按钮更快，点完直接落盘、可撤销。）

> ⚠️ **这一步原来写的是「用户决定投某个岗时，往 `job_search_tracker.csv` 里加一行」，
> 而同一份文件的 Step 0 第 2 条就写着「文件不存在（刚 clone 下来 ——
> **只有 `/job-outcome` 会创建它**）」。同一份文档里两句话对着干。**
>
> 链上的邻居也都不是这么做的：`/job-rank` 明写「**不要动
> `job_search_tracker.csv`**」，`/job-auto` 的铁律写着自己一个字不动它，
> `AGENTS.md` 那张衔接图里写回投递记录的是 `/job-outcome` 与 `/job-gmail-sync`。
> **只有这条搜索命令留着一个自己加行的口子。**
>
> 代价不是「多一行」：`/job-outcome` 那条路要问清发生了什么、归档材料、
> 写 `job-outcome.md`、再刷面板；从这里直接塞一行进去，那几样一样都没有，
> 而 Step 0 与 Step 4 又拿这张表去重 —— 一个半成品行会让这个岗**再也搜不到**。
> 2026-09-02 通读时发现。

## 铁律

1. **绝不编造职位。** 只摆真实来自 CLI 搜索/详情输出、或网络搜索结果的岗。
2. **去重不许省。** 摆出来之前，`seen_jobs.json` **和** `job_search_tracker.csv` 都要查一遍。
3. **跨城搬迁才是门，通勤时长不是。** 需要**跨城市搬迁**、而用户明确不接受的岗才跳过；
   **同城内通勤多远一概不跳过**——把距离如实写进提示，让用户自己权衡。
   这条原来写的是「clearly outside commute range 就 skip」，与 `04-job-evaluation.md`
   第 4.2 节**直接冲突**：通勤是连续量（45 分钟和 65 分钟没有本质区别，阈值定在哪
   都是武断的），而资料里那个通勤上限多半是 `/job-setup` 缺信息时填的、用户从没确认过的
   假设值——「最贵的判断 + 最弱的证据」。而且**这一步丢掉的岗连 `/job-rank` 都到不了**，
   用户永远不会知道有过这个岗。
4. **只要还开着的岗。** 截止日期已过、或者明写已关闭的，跳过。
5. **取详情要省着用。** 不要对每一条搜索命中都跑 `detail` 或网页抓取——**先按职位名和摘要粗筛一遍，只对看着有戏的才取。**

7. **体检有上限，而且要诚实。** Step 4.75 每家至多一次探测、一次重试，（`health` 模式下）至多取一次详情——**那是诊断，不是爬取**。**撞限流永远不算「坏了」的证据。** 体检结论只能来自实际看到的 CLI 输出；**没测成的渠道一律报「结论不明」，不许猜。** 体检能改的只有两样，都要先得到确认：`enabled` 开关，和**探通了的那条 CLI 的风控冷却**。
   后者是 2026-08-21 用户点名要的「CLI 应该有手动重试来检测是否恢复正常」——
   浏览器那条只有他本人过得了验证，而 CLI 那条**探一次就知道**；

   探通了就 `python tools/portal_budget.py --clear liepin-search`。

   ⚠️ **探测要穿过的正是它要测试的那道门**，所以额度检查换一条写法：

   ```bash
   python tools/portal_budget.py --check liepin-search --probe   # 探恢复专用
   ```

   `--probe` **只免风控冷却**，动作间隔照旧要守；
   **只对 CLI 渠道生效**（浏览器封的是账号，工具探不出来，探了也不作数）。
   不加 `--probe` 的普通 `--check` 会照常退出码 1 —— 那是对的，
   正常抓取本来就该被冷却拦住。
   **三条边界一条不放宽**：探测只在用户开口时做（不进常规轮次、不自动重试）；
   没通就照实说还在限流，不许因为「想让它通」多探几次；
   **浏览器那条永远不能这样解**——那要用户真的过完验证，工具探不出来。
